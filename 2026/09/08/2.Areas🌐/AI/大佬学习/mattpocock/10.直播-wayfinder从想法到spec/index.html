10.直播-wayfinder从想法到spec

发表于2026-09-08|更新于2026-09-08|2.Areas🌐AI大佬学习mattpocock
|总字数:2k|阅读时长:6分钟|浏览量:

Matt Pocock 是 TypeScript 教育者、Total TypeScript 作者，也是 AI 编码工作流的活跃实践者，维护着自己的 skills 仓库（开源）。这场直播演示的是他自研的 Wayfinder 工具——一个 agent 编排器，定位在”spec 之前的探索阶段”。

Wayfinder 是 GrillMe 技能的升级版。GrillMe 是单一 grilling 会话，而 Wayfinder 是 grilling 会话的编排器：它会先扫描代码库、理清现状，然后把一个宽泛的需求拆成多个聚焦的小 grilling 会话并行跑，每个会话对应一个决策点。最终输出是一份决策完备的 spec，可以直接交给实现 agent 去构建。

直播里 Matt 用一个真实需求做演示：给自己的 Course Video Manager（CVM）加一个 TikTok 创建器。从最初口述需求、让 Wayfinder 绘制”地图”、回答 grilling 问题、创建决策/研究/原型 ticket、并行多 session 推进、讨论 schema（format 用 enum 还是 boolean）、原型 UI 变体、到 render pipeline 归属和 TikTok posting lifecycle。整个流程把”雾里看花”逐步推成了清晰的 spec。

看点：

  • Wayfinder 如何把一个模糊需求拆解成 9 个可执行的决策 ticket
  • 决策 ticket vs 实现 ticket 的区别：前者靠做决策解决，后者靠代码实现
  • 多个 grilling 会话并行跑时怎么协调、怎么处理 blocking 关系
  • prototype 技能：把抽象讨论提升到可点击的 UI 保真度
  • Matt 对 model / harness / environment 三层架构的理解：换 model 不是唯一解
  • 真实工程权衡：enum vs boolean、Remotion 是否独立成仓库、TikTok 审计墙怎么绕

关键内容：

  • Opus 4.8 medium 足够用，不需要更聪明的模型，medium 在质量和延迟间最平衡
  • effort 权衡的是质量和延迟，越高边际收益越递减
  • agent = 新上下文窗口 + skill，所以自己用 skills 管理就够了，不一定要专门 agent
  • vibe coding 只在原型阶段，原型会喂给 spec，spec 才是真正发布的
  • Brownfield vs Greenfield 区分是胡扯，没大家想的差别那么大

00:01:11 真实需求：给 CVM 加 TikTok 创建器
00:02:25 Wayfinder 工作原理：绘制地图

cc自带一个agent管理，按 ← 键进 agent view 页面管理多Agent，在此处输入提示词就可以有新的Agent会话。作者认为Opus4.8做Grilling完全够用，没必要Fable5。

00:03:30 第一次 grilling：TikTok 视频的 schema

AI错误理解了tiktok的意思，作者希望复用video表的Schema，只需要加一个属性区分（比如上传方式），弹幕提到了omp的终端代理

分块并行

00:05:33 分块与并行：Wayfinder 的核心

引入了pitch的概念，对视频的包装/计划，准备好了之后就可以发布为视频，但作者认为短视频没必要规划，不需要关联pitch

作者提出了在spec完成后可以自己加一个review的阶段，是一个抓bug的好办法。（whisper flow输入）

三层架构

00:11:09 工作流定位：Wayfinder → to spec → to tickets → 实现 → review
00:13:13 提议地图与创建 GitHub issues

一般作者会过一遍这9个issue，直播跳过了。地图创建完毕后，里面内部主要就是派发的子任务和要创建的决策ticket

00:14:09 三层架构：model / harness / environment

有弹幕提到了opus不如gpt5.6，换个模型会不会更好。作者提出了自己看待Agent的理解Agent=LLM+harness，model只是最内层的，而harness就是cc codex，加起来才是agent，作者又在Agent外层加上了一层环境（文件/代码库等），他要说明的是模型只是一部分，另外一种免费的做法当然也可以增强harness或者说优化Agent所处的 环境。

00:16:33 Wayfinder 自动降级为 grill with docs

作者提到在更小范围的spec中，如果用了Wayfinder的话他有判断机制，如果范围小就不会建立map降级为grill的。

多会话协调

00:17:02 多 session 并行与 blocking 关系

作者梳理了当前ticket的关系，并指出Claude对一些任务直接进行派遣并行执行。

后续作者复制了ticket的地址，开一个新的会话，/wayfind url 就可以实现同时4个会话跑多个任务（claude这个agent并行管理的功能非常舒服）

有人提问：引用其他子技能组合为一个大技能，比如受控的循环工作流，这算好实践吗
matt作者不好评价，提到了writing-great-skill的技能，里面有针对skill编写的建议。

00:23:09 enum vs boolean 的工程权衡

这里就是作者的工程能力，新手可能认为就用boolean就行，但作者考虑到拓展型所以希望用enum来表示长短视频的状态更简洁

00:38:13 第二个原型：Studio 视图

作者提到不同worktree痛苦的点是要处理不同worktree的状态，可能依赖环境变量需要重新装，非常想把这些放远程服务器跑或者沙箱。

00:44:30 编辑面板的接缝分析

00:47:39 渲染管线归属决策

00:50:09 第三个原型：新版 Studio
00:53:03 对 Remotion caption 样式的执着

有人提问多个Agent并行，一个Agent决策是否会影响另一个，如果真的发生，就做一下Agent通信

  • 就先看这两个会话对冲的时候谁优先做，那先在grilling会话把他做掉，再做下一个
  • wayfind在blocking上做的挺好了已经

00:55:20 CVM 与 Remotion 的渲染契约
00:57:10 post 按钮的位置选择

审计墙

01:01:07 TikTok 审计墙：真 blocker

提问提到知识库放哪里会好，一般是个人wiki或者第三方google docs/notion

团队的.scratch协作（Issue Tracker）？不建议用本地markdown，作者目前是在Brownfield（大量遗留代码的半成品）代码使用wayfinder，不一定要在greenfield上用

因此真正的团队协作要跑一下/setup-matt-pocock-skills，明确使用真正的 Issue Tracker，可以用标签隔离，但不要把规划产物堆积在仓库内作为团队协作资产
