11.cc开发一个新功能

发表于2026-09-08|更新于2026-09-08|2.Areas🌐AI大佬学习mattpocock
|总字数:1.6k|阅读时长:5分钟|浏览量:

Matt Pocock（@mattpocockuk）在这期视频里完整展示了他用 Claude Code 给自己的真实项目开发一个新功能的全部过程——从模糊的想法到功能上线，每一步都讲清楚。

项目叫 course-video-manager，是 Matt 日常做内容的统一入口（录视频、管课程、写文章、做封面全在里面，约 1200 次提交、637 个 issue）。这次他想加两个功能：让 ghost lesson（只存在数据库、不在磁盘上的课程单元）能直接创建和删除，以及新增 ghost course（还没决定要不要做的规划中课程）。

整场不是概念科普，而是一个资深工程师真实的工作节奏：先用自己写的 grill-me skill 和 Claude 反复诘问需求，把模糊想法打磨成清晰的 PRD；用 Domain-Driven Design 的”统一语言”（ghost / real / materialize / materialization cascade）让 AI 协作更精准；再把 PRD 拆成 GitHub issue，交给 AFK agent（Sandcastle + Ralph loop）在 Docker 里自主实现；最后人做 QA，边测边把 bug 反馈成新 issue，agent 在后台并行修复。

他管这种模式叫”白班和夜班”——人负责想清楚要做什么，AI 负责把它实现出来。

看点：

  1. GrillMe skill 的实际用法——不是讲概念，而是看他真正在和 Claude 来回诘问需求
  2. DDD + AI 编程的结合——先敲定统一语言（ghost / real / materialize / cascade），再让设计和命名从语言中自然浮现
  3. 完整的”想法 → PRD → issue → AFK 实现 → QA 反馈”工作流，每一步都有取舍
  4. AFK agent 的执行环境 Sandcastle（Docker 隔离 + patch 回流）和 Ralph loop 的自主实现循环

关键内容：

  • 项目介绍：course-video-manager 是什么（React Router + TypeScript + Drizzle + Postgres + Vitest + Effect）
  • 需求澄清：GrillMe 诘问 ghost course 的 materialization cascade，推演 UI 权衡
  • 统一语言：Domain-Driven Design 的 glossary 如何让 AI 协作更精准
  • PRD 与 issue 拆分：从 GrillMe 对话产出 PRD，拆成四个可执行切片给 AFK agent
  • Sandcastle：Docker 隔离的 agent 执行环境，commits 作为 patch 回流到本地仓库
  • Ralph loop：自主实现 + 自动跑测试和类型检查 + 关闭 issue
  • QA 反馈循环：人在回路测试，发现 bug 立即建反馈 issue，agent 后台并行修复
  • 白班与夜班：朋友 Jamin 的比喻——人想清楚做什么，AI 把它实现出来

来源：

  • 作者：Matt Pocock（@mattpocockuk，Total TypeScript 创始人）
  • 原视频：https://www.youtube.com/watch?v=hX7yG1KVYhI
  • course-video-manager 仓库：https://github.com/mattpocock/course-video-manager
  • Claude Code for Real Engineers 训练营：https://aihero.dev/s/BQGSo5

00:00 开场与训练营介绍

作者的思路是把Agent看成团队委派任务的人，关注的是架构，反馈回路，而不是大量的前期工作

01:16 course-video-manager 项目介绍
03:18 想做的两个功能：ghost lesson 直建/直删 + ghost course
04:13 进入 VS Code 启动 grill-me skill

提出需求，不想必须创建ghost lesson后才能创建real lesson，删除也一样，以及ghost course的想法，这次grill的目的是产出文档，再拿去build

作者把认为这两个功能是一体的，就写在一个spec文档内了。

指出：跟LLM解释why是非常重要的（如果只有what意味着它没法根据你的想法给你替代方案）
比如他提出这个想法是因为想要更自由地规划课程而不用定死在文件结构上。

06:47 grill-me 的 explore 阶段与 sub-agent

随后cc进入explore阶段：把消息给新的subagent去探索代码库，把上下文摘要返回给父agent，所以这个过程可以节省token

08:17 介绍 Domain-Driven Design 的”统一语言”

DDD中的统一语言Ubiquitous Language 是用来打通开发者和领域专家的鸿沟，比如ghost lesson的概念是只存在于数据库但不在文件系统的lesson

09:16 grill-me 挑战痛点描述，发现 UI 缺口

这里作者只想简单问一下courseWrite service现状/结构/能力，可以用/btw

里面有一个course-write-e2e.test.ts，临时数据库，临时Git repo，把同步逻辑等进行测试，同时用到了Effect可以更轻松地进行单元测试，其他语言把这个当作一等公民。频道有一期专门就是讲Effect的。

11:34 推演 ghost course 的 materialization cascade

15:14 反复权衡：ghost course 里创建 lesson 的 UI

作者思考的时候已经在考虑哪一种UI使用更顺手干净了，同时由于共同语言，

在grill确认的越多，执行的就越顺利。在这个过程中会遇到取舍。遇到了难以理解的，会考虑做原型了

20:48 转到数据库 schema，讨论边界情况

棘手的边界改动，作者日历预留30分钟进行grilling，把功能想清楚是很正常的事情

23:01 决定满意，转入写 PRD

/ubiquitous Language 更新统一语言，跟上这里冒出的想法，后续materialization cascade这种词直接发出去，Agent也能懂，更新好后作者就提交了

24:47 调用 to-PRD skill，勾勒模块，写 PRD 并提交 GitHub issue

接下来主动说明调用/write的skill，提炼为总结文档，他一般不会看spec

29:32 PRD to issues，拆成四个可执行切片

通过/prd-to-issues来划分，确定阻塞关系

31:58 介绍 AFK agent 执行环境 Sandcastle（Docker 隔离）

在沙箱里做的commit会抽成patch应用到本地repo，会非常灵活

33:00 启动 Ralph loop，agent 自主实现

这个过程可以走开，或者新开一个grilling，在QA交付前，我们的活差不多了，剩下交给AI，有个很形象的比喻：白班（想点子-spce-issue）-夜班（AFK）

34:13 一个半小时后回来，review 提交，做 QA

提示词：拿最近5个commit，做一个QA Plan，存入github issue（后续他也考虑了将这个步骤都加入skill）

35:33 QA 反馈循环：发现 bug → 建反馈 issue → Ralph 后台修

发现在ui里作者加入了反馈问题的缓解，他会自动加入issue内

38:20 QA 中发现的设计问题：modal 复选框替代双按钮
41:42 继续多轮 QA + Ralph 并行修复

这也是为什么作者认为spec-code行不通的感觉，每次QA都会冒出难以处理的边界情况

43:46 总结：人 review 输入输出，AI 实现并行的协作方式
