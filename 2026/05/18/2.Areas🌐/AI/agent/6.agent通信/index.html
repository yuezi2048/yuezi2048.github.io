6.agent通信

发表于2026-05-18|更新于2026-05-18|2.Areas🌐AIagent
|总字数:12.4k|阅读时长:53分钟|浏览量:

本章解决的问题是：如何让多个智能体之间高效地交互，以及相互协作？

  • MCP（Model Context Protocol）用于智能体与工具的标准化通信
  • A2A（Agent-to-Agent Protocol）用于智能体间的点对点协作
  • ANP（Agent Network Protocol）用于构建大规模智能体网络

智能体通信协议基础

为什么要通信协议：提供标准化接口规范，用统一的方式访问外部服务，无须专门写适配器（类比TCP/IP让不同设备相互通信）

  • 工具集成的限制
    • 大量重复代码（HTTP请求，错误处理、认证等）
    • 难以维护：API变更需要修改所有工具
    • 无法复用：不同开发者写的工具兼容性问题
    • 扩展性：每添加一个服务就要写一个Tool类
  • 能力拓展瓶颈：无法动态发现、使用新的服务
  • 协作缺失：多个智能体（研究员、撰写员、编辑），只能通过手动编排来协调

三种协议设计理念比较

  • MCP（Model Context Protocol）：智能体和外部工具/资源 通信桥梁，让所有服务用统一规范访问，无需每个专门写个适配器维护
    • 设计亮点是：上下文共享。在RPC基础上，允许智能体和工具共享上下文信息（ 如下图连接到GitHub服务器后可以共享代码结构、依赖关系、提交记录）
  • A2A（Agent-to-Agent Protocol）：核心思路是实现智能体的点对点通信，如果说MCP关注的是智能体和工具的通信，A2A关注的是智能体和智能体的协作
    • 设计核心是：对等通信，即agent可以是服务者也可以是消费者，避免了中心化调节器的瓶颈，更灵活和可拓展
  • ANP（Agent Network Protocol）：目前是概念的框架，思路是构建大规模智能体网络的基础设施，如果说MCP解决的是如何统一访问工具，A2A解决的是如何点对点和智能体对话，他研究的是如何在大规模网络中发现和连接智能体。
    • 设计核心依旧是去中心化的服务发现，ANP核心是提供服务注册、发信啊、路由的机制，不需要配置连接就能动态发现网络中的服务

协议的选择根据实际需求：

  • 如果你的智能体需要访问外部服务（文件、数据库、API），选择MCP
  • 如果你需要多个智能体相互协作完成任务，选择A2A
  • 如果你要构建大规模的智能体生态系统，考虑ANP

通信协议架构设计

自底向上：

  • 协议实现层：MCP基于FastMCP，A2A基于a2a-sdk，ANP用轻量级实现提供基本的服务发现和网络管理做概念模拟，官方实现
  • 工具封装层 ：MCPTool、A2ATool 和 ANPTool 都继承自 BaseTool，提供一致的run()方法，智能体统一调用即可
  • 智能体集成层：智能体（ReActAgent、SimpleAgent 等）通过 Tool System 来使用协议工具，无需关心底层的协议细节。

本章应用为主，轮子不用太关注。

MCP基本连接测试

MCP

MCP 统一了智能体与外部工具的交互方式，像USB-C统一了设备连接方式一样，不需要对每个服务编写适配器代码，处理不同的 API、认证方式、错误处理等

整体架构（Claude Desktop为例，关键要明确MCP Client端的层级）

  • Host：Claude直接交互界面是Host，负责接收提问，管理对话流程
  • Client：当模型决定访问文件系统时，内置MCP Client被激活，内置Client会与MCP Server连接，发起请求并响应
  • Server：文件系统MCP Server被调用，就执行实际的文件扫描、访问目录等操作，最终返回文件列表
  • 为什么要划分？职责分离：
    • Host 专注于用户体验，Client 专注于协议通信
    • Server 专注于具体功能实现。开发者只需专注于开发对应的 MCP Server，无需关心 Host 和 Client 的实现细节。

MCP核心能力：Tool（主动）、Resources（被动）、Prompts（增强）

完整流程：建立连接——能力发现——多轮调用工具

LLM怎么决定调用何种工具？（可以看到，工具的选择是自动化的，需要更精细的工具描述）

  • 工具发现阶段：会得到所有可用工具的描述（名称、功能、参数等）
  • 上下文：将工具列表加入到系统提示词，让LLM特别关注调用工具的能力
  • 模型推理：分析问题和可用工具后，基于可用工具和上下文决策调用，随后Client交给Server来执行，返回的结果送回LLM，生成最终结果\

MCP和Function Calling区别？

  • 工具调用本身是LLM模型层的能力，关注的是模型知道如何调用相应的函数，没有统一规范，每加入一个可用工具，需要统一适配
  • MCP是作为通用协议的基础设施，关注的是工具和模型的连接，即插即用
  • 两者是相互协作的关系，工具调用是模型内在的能力，MCP是作为基础设施可以标准化地连接agent和工具

MCP传输方式

值得注意的是，MCP具备传输层无关性（Transport Agnostic），本身不依赖特定传输方式。有5种不同场景下的传输模式：

简单使用示例

  • HelloAgents中的MCPTool是用于Studio / Memory传输
  • MCP Client：建议HTTP/SSE远程传输

Memory Transport - 内存传输：快速原型开发，直接调用即可

Stdio Transport - 标准输入输出传输：本地开发调试，python/npx命令

HTTP Transport - HTTP 传输：生产环境，微服务架构

SSE Transport - Server-Sent Events 传输：实时通信，流式传输、长连接

StreamableHTTP Transport - 流式 HTTP 传输：双向流式传输场景

  • calculator_greet - 友好问候
  • calculator_get_system_info - 获取系统信息

A2A

传统的中央协调器（星型拓扑）的问题：单点故障、性能瓶颈（全部经过中央，限制了并发）、扩展困难（增加/减少要更改中心的逻辑）

P2P的优势：智能体能可以不依赖中央处理器直接通信，他的核心是任务Task和工件Artifact

A2A生命周期：创建——协商——拒绝 / 执行中（进行、暂停、完成、失败），从而实现进度跟踪

协商的认证流程：A2A代理发现、Auth身份验证、客户端发送消息 API 、服务端发送消息流 API

ANP

ANP 协议则专注于解决大规模、开放网络环境下的智能体管理问题，具体：

  • 服务发现：快速找到能完成任务的智能体
  • 智能路由：如果有多个智能体能处理，如何根据负载/成本选择最合适的分派
  • 动态拓展：新成员的加入如何被其他成员发现和调用

核心步骤：

  • 服务发现和匹配：Agent A通过Discovery服务，通过语义/功能描述查询，定位到符合任务需求的Agent B，发现服务爬取Agent B暴露的端点.well-known/agent-descriptions建立索引，从而完成匹配
  • DID身份验证：Agent A使用私钥对包含自身DID（去中心化信任根基）的请求签名，Agent B解析DID获取公钥，并验证签名的真实性和请求完整性，建立可信通信
  • 标准化服务执行：身份验证通过后，AgentB响应，双方通过标准接口和数据格式进行数据交换。

为什么要自己构建MCP服务

  • 封装业务逻辑：将企业内部特有的业务流程或复杂操作封装为标准化的 MCP 工具，供智能体统一调用。

  • 性能专项优化：针对高频调用或对响应延迟有严苛要求的应用场景，进行深度优化。
  • 功能定制扩展：实现标准 MCP 服务未提供的特定功能，例如集成专有算法模型或连接特定的硬件设备。

（1）什么是 Smithery？

Smithery 是 MCP 服务器的官方发布平台，类似于 Python 的 PyPI 或 Node.js 的 npm。通过 Smithery，用户可以：

  • 🔍 发现和搜索 MCP 服务器
  • 📦 一键安装 MCP 服务器
  • 📊 查看服务器的使用统计和评价
  • 🔄 自动获取服务器更新

需要注意的是，smithery.yaml是 Smithery 平台的配置文件：

配置说明：

  • name: 服务器的唯一标识符（小写，用连字符分隔）
  • displayName: 显示名称
  • description: 简短描述
  • version: 版本号（遵循语义化版本）
  • runtime: 运行时环境（python/node）
  • entrypoint: 入口文件
  • tools: 工具列表

pyproject.toml是 Python 项目的标准配置文件，Smithery 要求必须包含此文件，因为后续会打包成一个 server：

配置说明：

  • [build-system]: 指定构建工具（setuptools）
  • [project]: 项目元数据

    • version: 版本号（遵循语义化版本）
    • dependencies: 项目依赖列表

  • [project.urls]: 项目相关链接

总结

本章系统性地介绍了智能体通信的三种核心协议：MCP、A2A 与 ANP，并探讨了它们的设计理念、应用场景与实践方法。

协议定位：

  • MCP (Model Context Protocol): 作为智能体与工具之间的桥梁，提供统一的工具访问接口，适用于增强单个智能体的能力。
  • A2A (Agent-to-Agent Protocol): 作为智能体之间的对话系统，支持直接通信与任务协商，适用于小规模团队的紧密协作。
  • ANP (Agent Network Protocol): 作为智能体的“互联网”，提供服务发现、路由与负载均衡机制，适用于构建大规模、开放的智能体网络。

在HelloAgents框架中，这三种协议被统一抽象为工具（Tool），实现了无缝集成，允许开发者灵活地为智能体添加不同层级的通信能力：

实战经验总结

  • 优先利用成熟的社区 MCP 服务，以减少不必要的重复开发。
  • 根据系统规模选择合适的协议：小规模协作场景推荐使用 A2A，大规模网络场景则应采用 ANP。
