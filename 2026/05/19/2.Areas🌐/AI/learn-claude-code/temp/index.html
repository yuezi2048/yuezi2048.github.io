s01-loop

s01-loop：One loop & Bash is all you need

语言模型能推理代码, 但碰不到真实世界 – 不能读文件、跑测试、看报错。没有循环, 每次工具调用你都得手动把结果粘回去。你自己就是那个循环。

    • 👁眼睛：capture_output=True
    • 🛡保障：timeout截断

s02-tool handler

s02-tool handler：Adding a tool means adding one handler

只有 bash 时, 所有操作都走 shell。cat 截断不可预测, sed 遇到特殊字符就崩, 每次 bash 调用都是不受约束的安全面。专用工具 (read_file, write_file) 可以在工具层面做路径沙箱。

关键洞察: 加工具不需要改循环。

  • 通过handler维护的map来通过名称映射到函数，自主决定何时退出

s04-sub-agent

s04-sub agent：Break big tasks down; each subtask gets a clean context

Agent 工作越久, messages 数组越胖。每次读文件、跑命令的输出都永久留在上下文里。”这个项目用什么测试框架?” 可能要读 5 个文件, 但父 Agent 只需要一个词: “pytest。”

  • 用子代理的进程隔离来实现上下文隔离

  • 我们发现子代理返回给主代理只有最后一句总结的话返回，子代理处理过程中大龄纠错垃圾信息全部丢弃了

  • 我们发现细节：

    • 子代理是不包含task工具的，目的就是为了防止无限套娃
    • 子代理最小权限原则，探索代理只配 “查看权限”，既安全又高效

s04 >> Delegate: read all .py files and summarize what each one does

s05-skill

s05-skill：Load knowledge when you need it, not upfront

如果说 s04 解决的是长历史、多步骤引起的记忆通胀，那么 s05 解决的就是“由于规则太多、知识太杂引起的系统提示词（System Prompt）通胀”。

s05 引入的 双层技能动态加载（Two-Layer Skill Injection） 机制，彻底终结了这种浪费

  • 第一层：轻量级技能索引，递归扫描skills/ 目录下的所有 SKILL.md，但它只提取最顶部的 Frontmatter，这样在SYSTEM提示词中会很轻量
  • 第二层：大模型看到任务，发现命中skill描述的关键词，主动 load_skill，按需加载SKILL.md中复杂的规则进行执行（里面的执行内容视为工具执行结果返回）
    • 因为这是为了保持System Prompt静态，从而稳定缓存，所以选用tool_result的方式来注入上下文

s07-Task System（协调骨架）

Break big goals into small tasks, order them, persist to disk

s03 的 TodoManager 只是内存中的扁平清单: 没有顺序、没有依赖、状态只有做完没做完。

真实目标是有结构的 – 任务 B 依赖任务 A, 任务 C 和 D 可以并行, 任务 E 要等 C 和 D 都完成。

没有显式的关系, Agent 分不清什么能做、什么被卡住、什么能同时跑。而且清单只活在内存里, 上下文压缩 (s06) 一跑就没了。

解决：把扁平清单升级为持久化到磁盘的任务图。每个任务是一个 JSON 文件, 有状态、前置依赖 (blockedBy) 和后置依赖 (blocks)。可以免疫上下文压缩

任务图随时回答三个问题:

  • 什么可以做? – 状态为 pending 且 blockedBy 为空的任务。
  • 什么被卡住? – 等待前置任务完成的任务。
  • 什么做完了? – 状态为 completed 的任务, 完成时自动解锁后续任务。

这个任务图是 s07 之后所有机制的协调骨架: 后台执行 (s08)、多 agent 团队 (s09+)、worktree 隔离 (s12) 都读写这同一个结构。

  • task_update的联动更新逻辑，这是形成自动化流水线的关键。
  • 另外提供了task_list查看列表，get_task获取详情的接口，提升操作精度。

记忆管理

s06-Context

Context will fill up; you need a way to make room

上下文窗口是有限的。读一个 1000 行的文件就吃掉 ~4000 token; 读 30 个文件、跑 20 条命令, 轻松突破 100k token。不压缩, Agent 根本没法在大项目里干活。

使用三层遗忘机制：

  • micro_compact：每一轮（Every Turn）调用大模型前都会自动执行，维护滑动窗口，只保留最近 3 个（KEEP_RECENT = 3）工具的真实执行内容
    • 通过 tool_use_id 顺藤摸瓜，在历史消息里查出这个 ID 当时对应的是什么工具（比如 bash）。
    • 然后冷酷地把原先几千字节的庞大真实输出内容清空，替换成一句极短的占位符："[Previous: used bash]"。
    • 例外保护：特意跳过 read_file 工具的输出，避免Agent丧失对源码的记忆
  • auto_compact：token超过安全阈值，进行总结
    • 将messages 列表里之前成百上千条的繁杂历史一刀切掉、通通不要。取而代之的是，塞入一条唯一的、全新的、极其干净的 user 角色消息
  • compact工具：作为一个工具，让大模型选择性主动调用

它其实非常像 JVM 的分代垃圾回收机制（Garbage Collection）与操作系统的虚拟内存（Swap） 的结合体：

  • micro_compact（第一层） →\rightarrow→ 相当于 Minor GC：频繁、无感地回收那些朝生夕死的短命无用对象（过期的 Bash 输出），保持伊甸园（短期上下文）的清洁。
  • auto_compact（第二层） →\rightarrow→ 相当于 Major GC / Checkpoint 机制：当老年代内存（Token）快要溢出（OOM）时，触发全局熔断，把内存快照（Transcript）持久化 Dump 到磁盘（文件系统），然后利用大模型自身做一次“内存碎片整理（Memory Compaction）”，只保留高价值的对象。

并发

s08-Background Tasks

Run slow operations in the background; the agent keeps thinking

有些命令要跑好几分钟: npm install、pytest、docker build。阻塞式循环下模型只能干等。用户说 “装依赖, 顺便建个配置文件”, Agent 却只能一个一个来。

遇到一些长时间等待任务，交给后台线程干

  • 之所以使用守护线程：是为了防止主线程退出后，出现僵尸进程还在挂起的问题

在子进程的command方法执行完毕后，基于互斥锁线程将结果 安全插入队列

收件箱的消费：每次调用模型前来调用，这里不监听回调函数，就是为了解耦，后台线程无须关心主循环的时序

  • BackgroundManager.run 就是把任务扔进了 CompletableFuture.runAsync(() -> execute())，或者最原始的 new Thread(() -> execute()).start();
  • _notification_queue 就是一个内存级的 ConcurrentLinkedQueue
  • 主循环每次去 drain_notifications，本质上就是一个基于轮询（Polling）的消费者机制。

协作

s09-Agent Teams

When the task is too big for one, delegate to teammates（agent自己完成不了，就外包其他agent）

Subagent (s04) 是一次性的: 生成、干活、返回摘要、消亡。没有身份, 没有跨调用的记忆。Background Tasks (s08) 能跑 shell 命令, 但做不了 LLM 引导的决策。

真正的团队协作需要三样东西: (1) 能跨多轮对话存活的持久 Agent, (2) 身份和生命周期管理, (3) Agent 之间的通信通道。

这里采用的模型是领导-员工模式，每个成员维护一个基于文件的收件箱。（没有共享记忆、没有锁，所有沟通通过s07这种文件的方式协调，简单易于调试）

TeammateManager中config.json 维护团队名，整个团队谁在摸鱼谁在干活一目了然

spawn()创建队友，启用一个线程执行agent loop

  • lead（组长）执行 spawn_teammate("alice", "coder", ...) 时，系统在后台开启了一个永远不会自己 return 的守护线程（Daemon Thread）。
    • 哪怕 Alice 当前没什么事干（状态被标记为 idle），她的上下文记忆（messages）也依然保存在内存里。她就像一个坐在工位上待命的程序员，随时准备接收新的需求。

MessageBus（基于jsonl文件的消息总线）是append-only 的 JSONL 收件箱。send是追加一行，read_inbox() 读取全部并清空

  • 就是一个完全离线版的MQ：
    • 发消息（写）：当你想让 Alice 去检查一下代码时，调用 send_message("alice", "...")，底层其实就是以 append（追加）模式打开 alice.jsonl，把你的 JSON 消息塞到文件最后一行。这极其轻量且天然线程安全（因为是追加写入）。
    • 收消息（读）：看 MessageBus.read_inbox，它把文件里的所有行读出来，然后立刻清空文件（inbox_path.write_text("")）。这就完成了类似于 MQ 中的 Consume & Ack（消费并确认）机制。

依旧是s06中体现的亮点设计：主动拉取的循环机制，每个队友在每次 LLM 调用前检查收件箱, 将消息注入上下文，实现了解耦。

  • 当一封消息被塞进 alice.jsonl 时，Alice 的线程并不会收到任何中断信号或弹窗提示。大模型是被动的，它必须通过主动调用工具来“睁开眼睛”。
  • 我们发现了和子agent相似的思想：agent最小权限原则

这种异步轮询架构有一个核心缺陷：

场景：leader不想让alice干活了，发送send_message("alice", "...", msg_type="shutdown_request")，此时alice是毫无察觉的。

此时alice刚好又沉浸在等待网络IO，或者更糟糕地是，如果在跑超级长的工具

接下来终于在下一轮接收到了leader的shutdown的要求，

此时，我们发现Alice不会停下来，因为大模型不能直接控制Python的退出，他只会将其塞入到记忆中，带着这份停工信，继续浪费token

反思：异步轮询架构的痛点就是，缺乏硬中断机制，那么就引申出了每个Agent之间握手的协议，通过礼貌的谈判来优雅的关机从而解决这个场景的问题。

  • 我们发现通信过程中有各种类型msg_type：区分了私聊、群发、允许plan执行的ack（队友的计划要经过领导同意后再执行），关闭请求/响应（本次测试场景），这就是为了后续的协议铺垫。

s10-Team protocols

Teammates need shared communication rules

s09 中队友能干活能通信, 但缺少结构化协调:

关机: 直接杀线程会留下写了一半的文件和过期的 config.json。需要握手 – 领导请求, 队友批准 (收尾退出) 或拒绝 (继续干)。

计划审批: 领导说 “重构认证模块”, 队友立刻开干。高风险变更应该先过审。

两者结构一样: 一方发带唯一 ID 的请求, 另一方引用同一 ID 响应ACK。

类型协议 + request_id 凭证+ 状态追踪。

  • 类型强化：消息类型不再是模糊的 "message"，而是强制的 "shutdown_request"。
  • 凭证绑定：带上了一个类似订单号的 request_id。
  • 状态追踪：Lead 只要用 shutdown_response 工具查一下这个 request_id，就能知道对方到底停没停，是 pending 还是 approved。

队友收到请求后, 用 approve/reject 响应。

计划审批遵循完全相同的模式。队友提交计划 (生成 request_id), 领导审查 (引用同一个 request_id)。

  • Data_Agent 必须先调用 plan_approval 提交它的方案（例如：“我打算先跑文本的 embedding，再去跑图像的 resnet50”）。这会生成一个 req_id。
  • 这份方案进入 pending 状态。Data_Agent 的线程会挂起（因为没有得到 Lead 的回复信号）。
  • Lead 审查方案，发现它漏了多模态的交叉特征，于是调用 handle_plan_review(req_id, approve=False, feedback="必须先做表示失真的校准")。
  • Data_Agent 收到 rejected 信号和反馈，重新修改方案并再次提交。

一个 状态机（FSM）, 两种用途。同样的 pending -> approved | rejected 状态机可以套用到任何请求-响应协议上

通过这个机制就能解决确认对方的当前状态

我们发现他的关机/plan 请求内容是直接通过内存来存储的，鉴于s07的思路，我们应该是需要落盘到requests目录下

  1. 发起请求（Write）：当你（Lead）要求 Data_Agent 停止当前的文本 embedding 提取时，系统不仅发消息，还会立刻在 .team/requests/ 下生成一个 req_a1b2.json。
  2. 灾难发生（Crash）：Data_Agent 跑着跑着把 GPU 显存撑爆了，整个 Python 进程崩溃。
  3. 重启恢复（Recovery）：当你重新启动 Agent 团队时，Lead 在初始化阶段就会去扫描 .team/requests/ 目录。它会发现 req_a1b2.json 依然是 pending 状态，于是 Lead 会立刻知道：“哦，上次的关机命令对方还没确认，我得继续挂起等待，或者重新发送一次。”

这其实就是微服务架构中大名鼎鼎的 Saga 事务模式与 Outbox Pattern（发件箱模式）的雏形

此外，我们发现目前的情况是一种**“高度集权”**的环境，Alice和Bob依赖领导的发话才干活，好的员工看到看板上有peding的活会主动认领（Claim），这就是s11自主智能体的目标：

  • 空闲轮询（Idle Cycle）：没事干的时候，主动去翻 .tasks/ 看板。
  • 自主认领（Auto-claiming）：发现自己能做的任务，直接修改任务的 owner 为自己，然后开始疯狂干活。

s11-Autonomous Agents

Teammates scan the board and claim tasks themselves

s09-s10 中, 队友只在被明确指派时才动。领导得给每个队友写 prompt, 任务看板上 10 个未认领的任务得手动分配。这扩展不了。

真正的自治: 队友自己扫描任务看板, 认领没人做的任务, 做完再找下一个。

一个细节: Context Compact (s06) 后 Agent 可能忘了自己是谁。身份重注入解决这个问题。

赋予“下班权”：主动退出的 idle 工具

  • 代码截获到 block.name == "idle"，立刻 break 跳出昂贵的 WORK 阶段（调用 API），进入免费的 IDLE 阶段

队友循环分两个阶段: WORK 和 IDLE。LLM 停止调用工具 (或调用了 idle) 时, 进入 IDLE。

  • 空闲阶段循环轮询收件箱和任务看板。

任务看板扫描: 找 pending 状态、无 owner、未被阻塞的任务。

而在争抢claim的任务时，会上一把锁，保证只有一个队友拿到

身份重注入: 上下文过短 (说明发生了压缩) 时, 在开头插入身份块。

s12-WorkTree+Task Isolation

Each works in its own directory, no interference

到 s11, Agent 已经能自主认领和完成任务。但所有任务共享一个目录。两个 Agent 同时重构不同模块 – A 改 config.py, B 也改 config.py, 未提交的改动互相污染, 谁也没法干净回滚。

任务板管 “做什么” 但不管 “在哪做”。解法: 给每个任务一个独立的 git worktree 目录, 用任务 ID 把两边关联起来。

创建任务。 先把目标持久化。

创建 worktree 并绑定任务。 传入 task_id 自动将任务推进到 in_progress。

绑定同时写入两侧状态:

在 worktree 中执行命令。 cwd 指向隔离目录。

收尾。 两种选择:

  • worktree_keep(name) – 保留目录供后续使用。
  • worktree_remove(name, complete_task=True) – 删除目录, 完成绑定任务, 发出事件。一个调用搞定拆除 + 完成。

事件流。 每个生命周期步骤写入 .worktrees/events.jsonl:

事件类型: worktree.create.before/after/failed, worktree.remove.before/after/failed, worktree.keep, task.completed。

崩溃后从 .tasks/ + .worktrees/index.json 重建现场。会话记忆是易失的; 磁盘状态是持久的。
