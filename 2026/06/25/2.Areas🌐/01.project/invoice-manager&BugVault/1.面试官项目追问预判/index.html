面试追问预判 & 回答锚点

基于简历内容逐条埋点分析，按追问概率分三级。
面试前P0必背到脱口而出，P1熟读知道方向即可。

P0 — 必问（90%+，必须背到脱口而出）

1. MCP 到底是什么？和普通 API 接口、插件有什么区别？

简历埋点：链路编排 — 通过MCP协议严格隔离 | 兼容主流MCP客户端 | ADR含MCP vs Skill分析

回答框架：

MCP 是一套标准化的工具通信协议，做到”一次编写，所有 MCP 客户端通用”。

和普通 API 的区别：

  • API 是点对点对接，每个 AI 工具要自己写一套调用逻辑
  • MCP 定义了工具发现、调用、返回的统一格式，AI 可以自动识别和调用

和插件的区别：

  • 插件绑定平台（Claude插件/OpenAI插件/Cursor插件各一套）
  • MCP 基于 stdio 本地传输，不需要开端口、不需要公网
  • 数据完全不出本地，安全可控
  • 兼容 Claude、Cursor 等所有 MCP 客户端，不需要每个平台单独写适配器

项目印证：BugVault 5个工具注册后，Claude Desktop、Claude Code、Cursor 都能直接用，不用改任何代码。

参考文档：docs/refer/分析/02.为什么不做成skill.md

2. 为什么用 RRF 做融合，不直接给向量和全文加权重？

简历埋点：RAG链路设计 — RRF融合

回答框架：

向量相似度和 BM25 分数是两个完全不同量纲的指标：

  • 向量距离是 [0, 2] 的浮点数，分布取决于嵌入模型
  • BM25 分数是从 0 到几十不等的 TF-IDF 统计值

直接加权相加没有物理意义，结果很容易被某一路带偏。
比如某一轮 BM25 分数普遍偏高，权重就形同虚设。

RRF 是基于排名的融合算法，只看两路召回结果的排名位置，和分数大小无关。
K=60 是业界标准值，能保证同时被两路命中的文档总分显著高于单路命中的文档。
鲁棒性更强，是工业界双路召回的标准方案。

项目印证：BugVault 实测中，混合检索效果显著优于单路检索。

参考文档：src/bugvault/services/retrieval_svc.py rrf_fusion()

3. 父子分块是怎么设计的？解决了什么问题？

简历埋点：RAG链路设计 — 双表架构分离元数据与向量块，确保报错特征不被长方案文本稀释

回答框架：

之前单块向量的问题：
一条 Bug 记录包含标题、堆栈、尝试方法、解决方案等多段内容。
向量化是整段生成的，解决方案很长的时候会把报错的特征稀释掉。
比如搜 “KeyError: 42”，匹配到的可能是解决方案里恰好也提到了 KeyError，而不是真正的报错场景。

父子分块的方案：

  • 父表（bug_records）：存完整记录元数据
  • 子表（bugvault_chunks）：按两种类型分块存储
    • error_log 块：专门匹配精确报错特征（堆栈、错误消息）
    • semantic 块：匹配问题场景和解决方案的语义

检索流程：
chunk 级召回 → parent_id 去重 → 回查父表取完整文档 → Cross-Encoder 精排

这样就保证了精确报错的命中率，又不丢失语义匹配能力。

参考文档：src/bugvault/models/bug_record.py to_chunks()

4. Invoice 的 Agent 是怎么做到零侵入业务代码的？

简历埋点：Agent子系统 — 内部Token认证透传实现Agent层与Java后端松耦合

回答框架：

Agent 是一个独立的 Python FastAPI 微服务，和 Java 后端通过 HTTP 接口交互。

认证流程：
用户通过 Web 或微信登录后，登录凭证会透传到 Agent 层。
Agent 调用后端 API 时带上这个凭证（Cookie 或内部 Token），
Java 端的 AgentAuthFilter 拦截请求、解析身份、注入上下文，
后端业务代码完全感知不到 Agent 的存在。

带来的好处：
新增工具只需要在 Agent 层写调用逻辑，不用改后端业务代码。
不修改后端代码 → 不需要重新部署 → 不需要回归测试 → 业务零风险。
权限和后端 RBAC 完全一致，不会出现 Agent 能看到业务员不该看的数据。

参考文档：refer/invoice-mangager/invoice-agent-service/auth/context.py

P1 — 深挖防翻车（50% 概率）

5. RAG 评测是怎么做的？claim-level 评测具体逻辑是什么？

简历埋点：效果与质量 — simple/claim-level两阶段评测 | context_relevance + faithfulness

回答框架：

两阶段策略，按 eval_depth 参数切换：

simple（~300 tokens）：
快速整体打分，适合日常质量监控
→ context_relevance 0-5：检索结果和查询的相关程度
→ faithfulness 0-5：检索结果对源文档的忠实程度
→ rag_confidence_score = 两者之和（0-10）

claim-level（~1500 tokens）：
深度分析，适合 bad case 归因
→ Step 1：LLM 从检索文档中提取所有原子事实声明
→ Step 2：逐条验证声明是否被源文档支持（supported/unsupported/partial）
→ Step 3：faithfulness = supported_claims / total_claims

双重熔断器保护：
会话级配额上限（默认10次），超量自动降级为 simple
JSON 解析异常自动重试一次，失败后跳过评估不阻塞检索

参考文档：docs/refer/设计/evaluation-strategy.md

6. Cross-Encoder 和 Bi-Encoder 有什么区别？为什么精排用 Cross-Encoder？

简历埋点：RAG链路设计 — Cross-Encoder二次精排

回答框架：

Bi-Encoder：查询和文档各自独立编码成向量，用余弦相似度比较
优点：文档向量可预计算，检索速度快，适合召回阶段
缺点：查询和文档之间没有交互，丢失细粒度语义匹配

Cross-Encoder：查询和文档拼接后一起输入模型，输出相关性分数
优点：查询和文档有完整交互，精度更高
缺点：不能预计算，每对都要跑一次模型，速度慢

选型逻辑：
召回阶段用 Bi-Encoder（ANN 向量检索，快但粗）
精排阶段对 top-K 候选用 Cross-Encoder 二次打分（慢但准）
两者互补，不是替代关系，是漏斗型架构的两级

选型文档里有和 ColBERT 的对比：ColBERT 需要独立 PyTorch 索引（~1.5GB），
对于 20 条候选的重排场景，Cross-Encoder ONNX（1.1GB）精度更高、依赖更少。

参考文档：docs/refer/设计/adr-cross-encoder-vs-colbert.md

7. Agent 死循环怎么处理？工具调用出错怎么兜底？

简历埋点：Agent子系统 — AgentLoop设循环上限 | 每次调用写入日志

回答框架：

死循环处理：

  1. 硬限制：AgentLoop 设最大工具调用轮次，超限自动终止本轮
  2. 软约束：system prompt 明确要求单轮只调一个工具
  3. 可观测：每次调用写入日志（参数、耗时、结果），异常循环可追溯

出错兜底：

  1. ToolRegistry 统一 try/except 包裹，异常返回结构化错误信息
  2. 连续出错 N 次后 Agent 主动向用户报告，不静默重试
  3. P0 查询工具失败返回友好提示，不阻塞后续交互

参考文档：refer/invoice-mangager/invoice-agent-service/agent/loop.py

8. 为什么选 LanceDB 不选 Chroma、Milvus？

简历埋点：RAG系统 — LanceDB 向量+全文双索引

回答框架：

选 LanceDB 的原因：

  1. 零运维嵌入式 — 不用 Docker、不用单独部署，进程内嵌（向量界的 SQLite）
  2. 内置 FTS — 同时支持 ANN 向量检索和 BM25 全文检索，省掉 ES
  3. 列式存储 — 原生支持元数据过滤下推
  4. MVCC — 无锁并发读写，适合异步写入+同步读取

不选 Chroma：FTS 支持弱，混合检索需要额外搭 ES
不选 Milvus：太重，需要 Docker 等基础设施，不符合本地优先的定位

参考文档：docs/refer/分析/03.为什么选择LanceDB.md

P2 — 低频陷阱（20-30%）

9. 96% 测试覆盖率怎么算的？

避坑要点：
不要说「行覆盖率」，要说 功能特性覆盖率——137 个测试覆盖了核心功能点的 96%，
包含单元测试（模型/工具函数）、集成测试（chunk管道/MCP往返）、协议冒烟测试。
避免被追问行覆盖率统计工具和标准。

10. 70%+ 重复率降低怎么算的？

避坑要点：
必须明确限定场景：

  • 基于我个人开发过程中遇到的 Bug 记录
  • 回溯了约 2 个月的修复记录做的验证
  • 是小样本的验证结果，不是大规模企业级 A/B 测试
    诚实说清楚不扣分。

11. 6 篇 ADR 能说上来哪几篇？

避坑要点：
面试官可能让你具体讲讲。至少能说出 3 篇核心决策：

篇目 核心决策内容
MCP 协议选型 MCP vs Skill → 标准化、跨客户端、本地安全
LanceDB 选型 LanceDB vs Chroma vs Milvus → 嵌入式+FTS+MVCC
Cross-Encoder 选型 Cross-Encoder vs ColBERT → ONNX轻量、精度高、依赖少

剩下3篇可以提到：父子分块架构（chunk策略）、RAG评测体系（两阶段策略）、熔断降级设计（双路保护）。

避坑清单

坑 建议
主动提「商业化、卖给老板」 ❌ 不说，面试官不问不提个人规划
Skill 模板吹太满 ✅ 「当前是预置模板+基础统计，后续计划迭代」
运营看板说成「完善的数据平台」 ✅ 「基础统计+bad case归因，够日常使用」
70%+ 重复率说得太绝对 ✅ 「基于个人项目2个月回溯的验证，小样本」
96% 覆盖率说成行覆盖率 ✅ 「功能特性覆盖率，含单元/集成/冒烟测试」
被问「你和同学怎么分工」 ✅ 「我负责架构设计+前端+Agent+测试，他完成后端接口编码」

灵魂质问：「你这不就是在调 API 吗？」

这是 Agent 方向面试最常见的挑战，回答得好是加分项，回答不好直接减分。

核心逻辑：调 API 和搭系统是两码事

BugVault 的反驳链条

你说「这就是调API」 我可以回答「我解决的是这些工程问题」
Embedding 调一下 fastembed 多模型选型对比（BGE vs text-embedding-3-small），ONNX 本地 vs API 成本权衡
检索就是调 LanceDB query 双路召回策略设计（向量+全文为什么要两条路），RRF k 值怎么调，双表 why
评测调 LLM 打分 simple/claim-level 两阶段设计，熔断器阈值多少次，降级策略怎么定
保存就是 upsert 父子分块为什么这么分，MD5 去重键碰撞概率，自动 Schema 迁移兼容性

Invoice Manager 的反驳链条

你说「这就是调API」 我可以回答「我解决的是这些工程问题」
Agent 就是调 LLM AgentLoop 状态机怎么设计（BUILD/RUN/CONFIRM/RESPOND），防死循环轮次上限多少
工具就是调后端接口 意图路由策略（LLM 怎么知道该调哪个工具），参数校验怎么做的，异常怎么兜底
权限就是调 RBAC 双模式认证透传（Cookie + 内部 Token），后业务代码为什么不用改
记忆就是存 localStorage 跨会话记忆恢复怎么做到的，上下文窗口超出怎么截断

深度分析：发票查询场景要不要做 Agent 记忆？

这是面试中区分「调API」和「做架构」的关键一问。先给结论：

在发票管理这个业务场景下，不做长期记忆是正确的架构取舍，
30 分钟 Redis TTL 是合理边界。理由如下。

场景画像：发票查询 vs 通用对话

维度 通用对话（ChatGPT） 发票查询（Invoice Agent）
数据性质 无结构文本，跨轮依赖语义 结构化数据，每轮查询自包含
用户意图 延续话题、修正理解 查某张发票、统计某公司、登记一笔收支
关键信息 上轮说了什么 数据库里的业务记录
记忆价值 高（否则无法理解指代） 低（SQL 查一下就有）

为什么「查聊天记录」不如「查数据库」？

假设用户说：

「查一下 JH001 上个月的销项发票」

正确做法：Agent 直接调 query_invoice(company="JH001", date_range="2026-06") → 后端查 MySQL → 返回结果。

错误做法：Agent 先翻聊天记录「用户上个月是不是查过 JH001？」→ 没找到 → 再问用户 → 用户说 JH001 → 再查数据库。

结论：真实的业务上下文在 MySQL 里，不在聊天记录里。

30 分钟 TTL 为什么合理？

场景 TTL 内（正常） TTL 外（过期）
连续查发票 记忆正常，JH001 上下文延续 用户重新说「查 JH001」，唯一损失是少打了几个字
中断确认资金操作 _confirm_state 持久化，重启都能恢复 30 分钟不确认，业务上应该自动取消（本来就是这么设计的：60s 超时自动取消，Redis TTL 30min > 60s，不存在 TTL 先过期的情况）
跨天复用查询 — 用户重新说一次查询条件，Agent 重新查 MySQL 返回最新数据（数据比昨天更准，因为发票状态可能变了）

如果硬要做长期记忆，会引入什么问题？

方案 问题
MySQL 存聊天记录 存储爆炸：每条查询都存，一张表几百万行；检索困难：搜「JH001」可能命中 1000 条记录，不知道哪条有用
向量记忆（RAG on 聊天） 语义垃圾进垃圾出：聊天记录里是「查一下」「统计一下」「返回第 3 条」这类指令性语言，不是知识，向量化后互相打架
固定摘要 + 长期存储 维护成本高：摘要需要 LLM 生成，每轮对话都消耗 token；用户很少回看几天前的聊天

真正的记忆应该是什么？

总结

Invoice 会话记忆：Redis 挂了怎么办？

面试官可能问：你们用 Redis 做会话持久化，那 Redis 挂了怎么办？数据会丢吗？

回答框架：

丢了就丢了，这是业务场景决定的合理取舍：

  1. 会话 TTL 30 分钟，日常使用中用户持续操作会自动续期，
    真正过期丢失的场景是「用户离开了半小时以上」——回来后 Agent 不清楚之前的对话上下文。

  2. 但这不是问题，因为用户的业务数据没有丢——
    发票记录、银行流水、入账历史全部在 MySQL 里，Agent 查不了历史聊天，
    但能查「上个月开了多少发票」「JH001 客户的到款记录」这些真正有用的信息。

  3. 产品设计上初始化和用户的预期对齐：
    入口层提示「当前是新的会话，如有需要可重新说明查询条件」，
    就像 Claude Code 新会话不知道你昨天的操作一样——这是 Agent 产品的行业常态。

  4. 如果要解决，方向是让 Agent 从 MySQL 的业务日志里自动推断上下文，
    而不是把聊天记录当知识库存着。聊天记录是操作记录，不是知识。

延伸质疑：「BugVault 的 Hook + Skill 工作流，这不就是写脚本吗？」

面试官可能问：你在 BugVault 上写的 preflight/postflight，本质上不就是几个脚本调用 MCP 工具吗？这也算工作流编排？

回答策略：承认本质是脚本，但强调工程化的差异。
