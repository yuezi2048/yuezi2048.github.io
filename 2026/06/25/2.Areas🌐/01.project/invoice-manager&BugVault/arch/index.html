  • agent总结
    • Python
      • asyncio场景？
        • BugVault
          • JSON-RPC 通信是 async，MCP SDK基于asyncio
          • ThreadPoolExecutor 跑同步的 LanceDB / ONNX 操作，不阻塞事件循环
          • 异步写入：同步写 Markdown 归档（ms 级）+ 异步 fire-and-forget 向量入库
        • Invoice Agent
          • AgentLoop.run() 是 async 的，await LLM API 时不阻塞其他会话
          • Redis 操作用 redis.asyncio，不阻塞事件循环
          • 确认挂起用 asyncio.Event() + asyncio.wait_for() 实现超时
        • Fast API生命周期
          • 请求-FastAPI路由async Handler
          • await AgentLoop.run
          • AgentLoop 内部 await LLM 调用
          • await 后端 HTTP 请求
          • await Redis 保存会话
          • 返回响应
          • (单线程事件循环处理多个并发请求，I/O 等待时自动切换)
    • Agent
      • 循环&工具调用
        • 范式对比
          • ReAct
            • AgentLoop主体
          • Plan-and-solve
            • 适合复杂多步任务，发票场景不需要
          • Reflection
            • 资金安全保障
            • 跨会话改进是 Reflection（根因反思 + ADR）
        • 讲讲Agent Loop吧？
          • 流程
            • BUILD
              • SystemPrompt（日期&身份&可用工具）
              • 历史信息 + 当前信息 组装LLM请求
            • RUN
              • LLM返回Tool_call——query_invoice(company)
              • ToolRegistry参数校验—调用API——返回结果
              • LLM校验——决定是否继续调用工具
            • Confirm（仅P1资金工具）
              • 如果是P0就跳过
            • RESPONSE
              • 根据工具返回结果自然语言返回给用户
          • 亮点
            • 工具调用指令是LLM自动生成的Schema，不是硬编码
            • 参数校验在ToolRegistry做，不信任LLM的参数输出，如果错误则会打回给LLM重新输出
        • 你怎么保证没有死循环，工具调用怎么兜底的
          • 死循环：
            • 最大调用轮次+System Prompt+日志观测（参数、耗时、结果）
          • 出错兜底：
            • Tool Registry的try-catch返回结构化异常信息
            • 连续出错N次后主动向用户报告
            • P0查询工具失败 返回友好提示不阻塞交互
        • 意图路由怎么做的？（基于 Function Calling）
          • Tool 参数默认值 date_range 默认当月，company 默认从用户权限绑定的公司取
          • LLM 主动反问，如果信息不足会反问用户，对应的信息
          • 降级兜底，错误参数，后端API异常后，会告知用户确认查询条件
          • 为什么没有做分类器
            • 中小企业查询意图有限（发票 流水 统计 收支）
            • Function Calling 已经足够
            • 如果扩展到50+工具，才会考虑语义分类器预过滤
        • 为什么没用LangGrapth
          • 线性状态机没必要，增加抽象层
          • 自研Agent loop200行，可读性好
          • interupt机制比我们的确认机制更重
          • 多Agnet+图结构，才会考虑
      • MCP
        • MCP对比接口、插件、skill
          • 标准协议、点对点、工具调用统一格式
          • 插件绑定平台，MCP的stdio本地传输 客户端兼容
      • Skill
        • 涉业务/架构变更时触发的状态机讲讲？
          • 不是状态机，是责任链模式——每个环节决定「继续还是跳过」
            • 门槛+session缓存+可用性
      • 怎么做到零侵入已有业务代码
        • FastAPI服务，java后端通过HTTP接口交互
        • agnet调用时权限怎么保证的
          • 权限层
            • 登录后，凭证透传到Agent层 后续调用带上凭证
            • Java的AgentAuthFilter拦截请求验证身份 注入身份信息等上下文 好处就是不影响业务代码 且接口感知不到Agent存在
          • 调用过滤
            • Tool Registry会校验当前工具是否确认，也会拦截非法调用
            • 即使传入了有害代码，也会只限制在8个工具的能力边界内
          • 上下文隔离
            • 不同用户token不共享，Agent不知道其他用户token
            • Agent日志的token会脱敏
        • 你2.0提到了业务规则 那100w行老系统要集成Agent辅助 与1.0的BugVault区别？
          • 区别
            • 索引策略：errorlog+sematic覆盖的是单次修复场景，老系统可能模块+文件+函数 索引维护
            • 检索优先级：原先是tech_stack过滤，后续可能要考虑「调用链路 + 修改频率」
            • 记忆粒度：原先存的是bug修复记录，后续应当就是模块的设计约束，接口调用规定
          • 但不变的是
            • 双路召回 + RRF 融合 + Cross-Encoder 精排
            • MCP 协议注入，不侵入工具本身
            • 本地优先、数据安全
        • 资金操作工具的幂等性和安全性
          • 幂等性
            • 接口保证事务 + 唯一约束，第二次请求会被第一次拦截
            • Agnet确认机制，保证用户确认后才请求，不会因为LLM幻觉自动触发资金操作
          • 安全性
            • Cookie（Web） + 内部 Token（微信）认证
            • RBAC权限透传：Agent权限和Java业务一致
            • 敏感操作二次确认
            • 60s无操作自动取消，不残留待执行状态
        • 定时对账和定时任务有什么区别？
          • 定时任务：固定SQL+固定格式+固定推送管道
          • 定时Agent：触发条件+LLM动态生成结论+判断异常数据+生成可读的摘要和风险预警+推送企业微信
            • Agent 可以理解「年底要关注坏账计提」这个上下文。
            • 虽然目前还比较弱，只有触发是自动的，完全体应当是发现异常后可以主动编排进行后续的动作 这是后续的迭代方向
      • 运维
        • 讲讲数据看板的实际Bad Case吧？
          • 查发票工具调用成功率98突然降到72
          • 「查一下上个月的发票」 成功调用query_invoice但没有date)range参数 导致全表搜索，响应超时
          • 排查：system prompt 里「date_range 必填」的指令不够突出，导致模型不给参数
          • 修复：
            • query_invoice的schema加入当月的默认值
            • Prompt将date_range必填放在最前面
            • 监控层告警，date_rage调用工具参数丢失时告警
            • 修复后，成功率恢复90+
    • RAG
      • 分块
        • 父子分块（怎么设计的，解决了什么问题）
          • Bug包含标题、错误栈、尝试方法、最终方案
            • 向量化容易稀释掉报错栈的特征 尤其是尝试方法中包含了报错的描述
            • 父子分表： 父表存完整记录，子表error_log+sematic
              • error_log精确匹配报错特征
              • sematic匹配场景和解决方案语义
      • 向量数据库
        • LanceDB（为什么）
          • LanceDB优势
            • 运维：无需单独Docker部署，进程内嵌（向量版的SQLite）
            • 内置FTS：原生支持ANN BM25全文检索，无需ES等
            • 列式存储：原生支持元数据过滤下推
            • MVCC：无锁并发读写，异步写入，同步读取
          • 不选择其他原因
            • Chroma：FTS 支持弱，混合检索需要额外搭 ES
            • Milvus：太重，需要 Docker 等基础设施，不符合本地优先的定位
      • 混合检索
        • RRF融合权重（为什么不向量和全文用权重）
          • 向量距离是[0.2]浮点数，取决于向量模型 BM25是0到几十的TF-IDF统计值
          • 加权相加容易被一路带偏 所以基于两路的排名，而不是分数加权
          • 选用K=60是业内双路召回标准方案 保证双路召回文档总分高于单路
          • 举例说明 Bad Case
            • 纯语义： Python ModuleNotFoundError: requests语义搜到：「Node.js 中 Error: Cannot find module ‘axios’」
            • 纯BM25: 连接超时搜到的是「连接超时」四个字的服务器配置，但用户想要的是requests库超时案例
            • 双路召回： 向量捕捉Python+模块找不到 BM25捕捉NotFound报错关键词精确匹配 两路top_4 -> RRF融合，同时命中的文档总分显著高于单路，既懂找什么，又能匹配语义
        • chunk召回
        • parent去重
        • 回表
        • cross-encoder重排序
          • 这是什么？为什么用这个？
          • 延迟多少？用的什么模型？蒸馏缓存等优化考虑过？
            • jina-reranker-v2-base-multilingual（1.1GB），ONNX CPU 推理
            • Subtopic 2top-K=20 时精排阶段约 50ms，相对召回阶段的 ~5ms 是可接受的
            • 没做蒸馏
              • 50ms（整体200ms）可接受 蒸馏需要数据标注和训练pipeline，个人项目投入产出比不高 top-k如果到100+，可能会考虑
            • 缓存（同一 session 内相同 query 的精排结果直接返回）
              • 但实际上精排的输入是 query + document pair，不怎么命中
          • 和 Bi-Encoder 有什么区别
          • Bi-Encoder：查询 / 文档都编码向量 余弦相似度比
            • 文档预计算，召回速度快 查询和文档没有交互，缺少细粒度语义匹配
          • Cross-Encoder：查询和文档拼接后给模型 输出相关性分数
            • 查询和文档有交互，精度高 不能预计算，每次要跑一次模型，速度慢
          • 选型
            • 召回使用Bi（ANN向量检索快速粗排）
            • 精排使用Cross进行Top-k候选二次打分
          • 为什么没用更先进的ColBERT
            • ColBERT需要构建Pytorch索引 1.5GB 而当前候选20的场景 Cross-Encoder ONNX依赖更少，精度更高
      • 评测（怎么做的）
        • 二阶段评测（Simple+Claim+双重熔断器）
          • simple:context_rel(0-5) + faithfulness(0-5) rag_confidence_score两者之和
          • Claim: 适合bad case归因 LLM检索出原子事实声明 逐条验证声明是否被源文档支持（supported/unsuported/partial） faithfulness = supports_claims / total_claims
          • 熔断保护：会话上线10次claim，超过降级simple JSON解析失败会重试，失败后跳过不阻塞检索
        • 熔断做的是try-catch还是断路器模式？
          • 第一层：会话计数器（熔断器half-open简化）
            • 一个Session初始化_claim_counter，默认10
            • claim-level评估前counter += 1
            • 超过10次降级simple，新建Session则恢复
          • 第二层：异常捕获兜底
            • 强制输出合法JSON，如果失败重试
          • 不是基于失败率的状态机（Closed → Open → Half-Open），而是基于使用量的配额制 + 异常兜底。
    • 软实力
      • 指标
        • 96% 测试覆盖率怎么算
          • 不是行覆盖率，是功能特性的覆盖率
            • 单元测试-模型/工具函数
            • 集成测试-chunk管道/MCP往返
            • 协议冒烟测试
        • 70%+ 重复率降低怎么算
          • 基于个人使用中的真实Bug
          • 回溯近两个月的bug，是小样本的验证结果
          • 并不是大厂的A/B测试
        • 6 篇 ADR 说说？
          • MCP选型、LanceDB选型、Cross-Encoder选型
          • chunk策略（父子）、Rag评测、熔断降级设计
      • 技术决策
        • 早期「父子分块」策略的块大小是凭感觉 error_log chunk 设为 512 tokens、semantic chunk 设为 1024 tokens
        • 发现一些跨多行的堆栈被截断了， 导致 error_log 块匹配不到完整的报错信息
        • 启发：chunk_size要有数据支撑，要基于实际数据分布来定，不同场景应当有不同的块大小策略
      • AI看法
        • 趋势是多Agent协作，但编排还在探索 从通用到垂直领域Agent 从对话式到嵌入式，可以集成到ERP等系统
        • 瓶颈： 评测体系：端到端执行 / 工具调用成功、成本/效率 记忆上下文管理：如何在大量上下文信息定位有效信息，跨会话记忆怎么做（BugVault就是尝试） 可靠性可观测性：一旦进入生产环境，为什么做这个更重要，bad case 归因
    • 灵魂拷问
      • 不就是调用个API吗？
        • 点破调用API和工程师搭建系统的误区
          • 调API：拿 SDK 调通接口，返回结果展示出来
          • 搭系统：选型、集成、编排、兜底、评测、迭代
        • BugVault
          • Embedding不就是调一下fastembed
            • ONNX 本地 vs API 成本权衡
            • 多模型选型对比 （BGE vs text-embedding-3-small）
          • 检索不就是调LanceDB query
            • 双路召回策略设计 （向量+全文 双路）
            • RRF的k值调优
            • 父子双表设计
          • 评测不就是调 LLM 打分
            • simple/claim-level 两阶段设计
            • 熔断器阈值多少次，降级策略怎么定
          • 保存进去不就是upsert
            • 父子分块为什么这么分
            • MD5 去重键碰撞概率
            • 自动 Schema 迁移兼容性
        • Invoice Manager
          • 感觉你这Agent就是直接调LLM
            • AgentLoop 状态机怎么设计（BUILD/RUN/CONFIRM/RESPOND）
            • 防死循环轮次上限多少
          • 工具不就是调后端接口
            • 意图路由策略（LLM 怎么知道该调哪个工具）
            • 参数校验怎么做的
            • 异常怎么兜底
          • 权限不就是原来的RBAC
            • 双模式认证透传（Cookie + 内部 Token）
            • 后业务代码为什么不用改
          • 记忆是存在LocalStore？
            • 跨会话记忆恢复怎么做到的
            • 上下文窗口超出怎么截断
      • 那你这发票场景怎么没做记忆呀？
        • 不做长期记忆只用Redis的TTL是架构取舍 我们可以对比一下通用对话豆包的场景
          • 记忆价值：低-只需要SQL查就行 vs 高-需要理解
            • 数据性质：结构化数据 vs 依赖语义无结构文本
            • 用户意图：业务crud vs 延续话题/修正理解
            • 核心信息：数据表业务数据 vs 上轮对话内容
          • 真实的业务上下文是在数据库中，而不是在聊天记录里
        • 为什么使用30分钟
          • 30分钟内，能连续查发票、重启能恢复
          • 30分钟外，数据的及时性，业务的取消
        • 长期记忆的问题
          • MySQL方案：存储爆炸、难以检索
          • 向量数据库RAG方案：指令性的语义垃圾多
          • 固定摘要：维护的token成本，并且回看的需求不大
        • 真正的记忆（权限是什么，公司有哪些，查询模式）
          • 用户行为日志、权限表、业务配置表
        • 部分的妥协：记忆最近的查询条件
      • 那你用Redis，服务挂了数据怎么办
        • 降级：退化纯内存，不影响会话
        • 双重缓存：Redis启动时数据能自动恢复
        • 状态可恢复：中断确认进度做了序列化
        • Redis和服务同时挂了的情况数据会丢，但在业务里可允许，
          • 正常过期是30分钟外的TTL过期数据
          • 但业务数据是永久保存在MySQL中
          • 后续：可以根据MySQL日志来推断上下文
      • BugVault的工作流不就是脚本吗？
        • 确实是，但形成可复用、可诊断、可扩展的工程化封装才是目标
          • 标准化入口、结构化输出、 与BugVault深度集成-自动查经验，存记录 编排而非单步：多个子skill串联，有异常处理
          • 如果只看他是否为脚本，那CI/CD k8s也是脚本
