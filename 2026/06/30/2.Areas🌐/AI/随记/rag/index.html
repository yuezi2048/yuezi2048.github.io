为什么要RAG：LLM存在固有知识、幻觉问题，RAG的则可以动态地为 LLM 注入外部知识。这一过程的核心是语义检索，但其依赖高质量的向量嵌入。

  • 分块（向量检索和模型处理的基本单位）
    • 为什么要分块：嵌入模型上下文窗口（如bge-base-zh-v1.5限制512token）、LLM的窗口（一般百万token上下，但包含用户问题、提示词等）
    • 那直接分块上限不行吗？过大的窗口信息会稀释、Lost in the Middle、一个好的分块应当明确且相互独立
      • Transformer：分词器将文本划分token（Tokenization）——然后会对token高维向量化（Vectorization）——通过[CLS] mean pooling等方式压缩成一个向量来表示语义（Pooling），这意味着模型看到的是压缩的向量，当一块文本包含信息过载，就会忽略细节特征。
    • 分块策略（LangChain源码中）：
      • 固定大小（实际上并不是固定，优先保证连贯性，如果超过size会结束，如果一个段落超过了size会放入并警告，以及重叠长度）：
        • 段落分割（CharacterTextSplitter按分隔符\n\n或者正则）
        • 智能合并（将分割段落合并，超过chunk_size后再生成新块，通过chunk_overlap重叠保证上下文连续）
        • 场景：固定大小牺牲一定连贯性换取开销速度，适合日志、数据预处理
      • 递归字符（长文本处理）
        • 分隔符层级递归切分（RecursiveCharacterTextSplitter）
        • 递归分块会继续使用更细粒度的分隔符（句子→单词→字符）直到满足大小要求（相比上一个警告并保留会好很多）。
      • 语义分块
        • 断点识别（评估语义的差异）：百分位法、标准差法、四分位距法、梯度法
      • 基于文档结构分块（如Langchain的MarkdownHeaderTextSplitter）：先按标题分组，再按需细分
        • ，既保留了文档的宏观逻辑结构（通过元数据），又确保了每个块的大小适中

索引构建

  • Embedding：将处理好的chunk基于语义的Embedding高维嵌入 存入 向量数据库，便于我们用余弦相似度（点积 正则化）、欧氏距离 来衡量与查询语义的差距，进而进行后续的召回

    • 一个好的Embedding应当捕捉问题和文档之间的深层语义联系

  • 构建思路演进

    • 静态嵌入：Word2Vec （ Skip-gram 和 CBOW 架构，国王 - 男人 + 女人 ≈ 王后）GloVe （全局词-词共现矩阵）等，但无法处理一词多义。

    • 动态上下文嵌入：Transformer（Self-attention，生成词向量动态考虑其他词），BERT（加入MLM掩码等自监督任务 生成上下文嵌入），解决了一词多义难题。

    • 更高质量的嵌入：微调或指令（INSTRUCTOR 模型）适应特定领域语义、支持多粒度多模态（CLIP、bge-visualized-m3)）、支持混合检索（BGE-M3）

      • CLIP是双编码器架构，图像+文本映射到共享向量空间中，通过对比学习训练双编码器，对齐图文向量空间。赋予了零样本（Zero-shot）识别能力，无需微调就有泛化的理解（如传统的分类任务，判断是否为猫，计算和对应文本的相似度即可）

  • 当前整体嵌入思路：一般是BERT变体，堆叠多个 Transformer Encoder 层作为双向表示学习网络。

    • 掩码语言模型MLM：掩盖15%加入[MASK]，让模型预测原始token，被迫学习token和上下文语义关系
    • 下一句预测NSP：构建A和B训练样本，50% B是A的真实下一句（isNext），剩下的是随机下一句（notNext），判断B是否是A的下一句，被迫学习句子连贯性
      • 但后续预训练模型（如 RoBERTa、SBERT）发现NSP任务可能损害性能， 在预训练阶段移除了 NSP
    • 现代模型针对性策略：
      • 度量学习：直接以“相似度”作为优化目标，如（问题，答案）训练这些成对文本的相对距离，将负例推远。
      • 对比学习：将相似的样本（Anchor-Positive）“拉近”，将不相似的样本（Anchor-Negative）“推远”，通过构建三元组（Anchor, Positive, Negative）

  • 嵌入模型选型思路

    • 确定baseLine：MTEB (Massive Text Embedding Benchmark) 给出在特定数据集上的分类、聚类、检索、排序具体排名
      • x-y：参数量（模型潜力，计算资源）-任务得分（通用语义理解）
      • 气泡：大小是维度，颜色是最大处理长度
    • 根据业务构建私有数据集，典型问题+标准答案
    • 迭代优化：评估其召回的准确率和相关性，不断更新模型、调整RAG的环节（分块策略等）。

  • 向量数据库：

    • 为什么需要

      • 相似度检索：通过标量索引（如BITMAP）和向量索引（核心，HNSW IVF），大数据量下毫秒级别的ANN找到最相似的数据

        • 基于树的方法：如 Annoy 使用的随机投影树，通过树形结构实现对数复杂度的搜索
        • 基于哈希的方法：如 LSH（局部敏感哈希），通过哈希函数将相似向量映射到同一“桶”
        • 基于图的方法：如 HNSW（分层可导航小世界图），通过多层邻近图结构实现快速搜索（可载入内存，低延迟）
        • 基于量化的方法：如 Faiss 的 IVF（倒排文件，聚类分桶，先找最相似的桶再精确搜索） 和 PQ，通过聚类和量化压缩向量（可载入内存，追求吞吐）
        • 补充：Milvus还提供了FLAT暴力搜索（高精度慢速度），DiskANN的方案（无法载入内存的海量数据）

      • CRUD：高维向量CRUD，查询可以支持标量字段过滤（如日期范围、聚类分析等业务个性化需求）

      • 生态：可以便于LangChain、LLamaIndex和机器学习工作流的集成

      • 维度 向量数据库 传统数据库 (RDBMS)
        核心数据类型 高维向量 (Embeddings) 结构化数据 (文本、数字、日期)
        查询方式 相似性搜索 (ANN) 精确匹配
        索引机制 HNSW, IVF, LSH 等 ANN 索引 B-Tree, Hash Index
        主要应用场景 AI 应用、RAG、推荐系统、图像/语音识别 业务系统 (ERP, CRM)、金融交易、数据报表
        数据规模 轻松应对千亿级向量 通常在千万到亿级行数据，更大规模需复杂分库分表
        性能特点 高维数据检索性能极高，计算密集型 结构化数据查询快，高维数据查询性能呈指数级下降
        一致性 通常为最终一致性 强一致性 (ACID 事务)

    • Milvus说明：组件可以比喻成图书馆：Collection（图书馆，类似Table，是基本单位）->多个Partition（分区）->Schema（图书字段卡片）->Entity（书本身）->Alias（动态推荐书单，方便应用层切换）

      • Collection需要优秀的Schma定义字段：新闻文章为例（典型的多模态、混合向量 Schema 设计场景）。将一篇文章拆解为：唯一的 Article (ID)、文本元数据（如 Title、Author Info）、图像信息（Image URL），并为图像和摘要内容分别生成了密集向量（Image Embedding, Summary Embedding）和稀疏向量（Summary Sparse Embedding）
      • 分区的意义：查询性能（减少范围）、便于管理
      • Alias可以实现在应用层安全更新数据
      • 检索说明：近似最近邻 ANN 是利用好索引，快速找到相似向量TopK，并不是暴力而是精度和速度的权衡结果
        • ANN增强策略：范围检索 （特定范围，人脸/异常识别等场景）、多向量混合检索（RRF排名平衡 WeightedRanker加权，这里是用到了并行检索+rerank融合，增强RAG）、分组检索（比如数据库文档，保证来自不同的来源场景）

    • 索引优化：

      • 上下文拓展：小块文本精度高但缺乏上下文，因此引入LlamaIndex的句子窗口检索。先聚焦精确句子，再生成答案前扩展成更大的窗口，同时兼顾精度+上下文（气候报告案例，更详尽和连贯）
      • 结构化索引：对索引加入元数据，便于定位
        • MarkdownHeaderTextSplitter在分词时就可以将各级标题提取出来后存入元数据中，可以直接服务元数据过滤
          • 思考：比如LlamaIndex 的PandasQueryEngine要eval执行python代码很危险，我选择创建摘要索引（便于路由）和内容索引（加入年份等元信息）（电影按年份路由问答案例）

检索优化

  • 混合检索（获得更鲁棒、更准确结果，关键词稀疏向量+语义密集向量）

    • 向量说明
      • 稀疏TF-IDF（BM25），可解释性好，每个维度有确切的词，专业名词可以精确匹配，但同义词无法识别
      • 密集， （如早期的Word2Vec、GloVe），可以理解同义词，泛化能力好，但可解释性差，需要算力训练，对于未登录词OOV（解决是子词分割，如BPE、WordPiece）处理不好
    • 混合策略：
      • RRF倒排融合
      • 加权线性组合（归一化相加，比较好控制比例）

  • 查询构建（除了语义匹配，业务需要复杂的过滤、聚合等，思路是通过LLM将自然语言转换成结构化的请求）

    • 元数据文本：chunk一般会有元数据MetaData，在LangChain中有一个Self-Query Retriever，效果就是查一下2022年发布的机器学习的论文，就会自动把2022加入到MetaData，查询字符串就是精简的机器学习论文
    • Cypher：可以衍生到图数据库Neo4j等表示匹配图的模式和关系（如一个人和一个国家的居住在的关系），Langchain提供了GraphCypherQAChain进行转换
    • Text2SQL：在结构化数据中，MySQL中也是重点，翻译成能直接执行的SQL语句
      • 挑战：幻觉输出（few shots，RAG、自纠错）、数据库理解（要求更精确的Create Schema）、用户输入的模糊性
      • 其中RAG除了DDL，还需要有表字段业务描述、业务术语同义词、复杂的查询样例（JOIN GROUP BY等特殊业务场景）
      • 为什么不建议用框架：黑盒问题，你很难判断是RAG还是检索，还是SQL生成的问题，比如上一节LangChain搭建搜索最短bili视频的查询异常，其实很难调试

  • 查询重构与分发（查询翻译、查询路由）

    • 查询翻译：提示工程、多查询分解(Multi-query)、退步提示Step-Back Prompting、假设文档嵌入 (HyDE)
      • 提示工程：如SelfQueryRetriever最短视频没法处理比较的场景，就可以通过提示词来处理这种场景
        • 退步提示：提升推理能力的提示词技巧，在细节繁多的问题且COT表现也不好的情况下，我们可以退后一步更抽象的问题（Step-back Question，如让他分析体积增加时气压变化，不如先让他思考背后的物理原理），让AI被迫思考问题背后的原理和概念，接下来他就会推理这个退步问题的答案，并基于该上下文解决具体问题。
      • 多查询分解：复杂的问题拆分成子问题，对子问题进行检索、合并、去重（如你对人工智能和当下职业裁员的看法就可以拆分）
      • 假设文档嵌入：用户请求简短，所以就生成一个语义相近的虚拟答案靶子作为标准答案，编码后返回最相关的内容
    • 查询路由：数据源（意图）路由（常见 不同的意图定位不同数据库）、组件路由（根据问题复杂度，来直接向量 / Agent）、提示模板路由（优化生成）
      • 意图识别：LLM构建“分类-分发”的流水线（分类器、路由分支、组合链条），在Langchain中有LCEL6这样的链条声明参数，将组件进行串联。
      • 嵌入相似性路由：计算嵌入相似度进行。

  • 检索进阶

    • 重排序：RRF（零样本重排）、RankLLM、CrossEncoder（查询&每个候选文档输出分数，需要n次模型推理）、ColBERT（优化效率，独立编码后期交互策略，计算查询token和文档中每个token的最大相似度，最后聚合最大相似度作为相关性）

    • 特性 RRF RankLLM Cross-Encoder ColBERT
      核心机制 融合多个排名 LLM 推理，生成排序列表 联合编码查询与文档，计算单一相关分 独立编码，后期交互
      计算成本 低（简单数学计算） 中 (API 费用与延迟) 高（N次模型推理） 中（向量点积计算）
      交互粒度 无（仅排名） 概念/语义级 句子级（Query-Doc Pair） Token 级
      适用场景 多路召回结果融合 高价值语义理解场景 Top-K 精排 Top-K 重排

    • 压缩：检索到的chunk的后置处理，提炼关键内容，过滤噪声，避免信息过载影响LLM输出

      • Langchain提供ContextualCompressionRetriever来内容提取，我们一般可以自定义重排器和管道（如ColBERT重排器集成压缩），探索思路
        • 官方文档定位到DocumentCompressorPipeline可以组合压缩器，发现没有提供ColBERT重排功能，分析CompressionRetriever源码，得出是base_retriever得到原始文档，再由base_compressor进行压缩重排，得到核心基类base_compressor接收的核心参数对象BaseDocumentCompressor，参考其他实现的类，和使用案例，进行改造即可
        • AI改造说明：需要提供给大模型的关键信息BaseDocumentCompressor 的源码和 ContextualCompressionRetriever 的源码及其使用示例、你的明确目标（实现 ColBERT 重排逻辑）、以及 LangChain 中其他重排器的代码作为参考。信息越充分，模型生成的代码越准确

    • 校正：检索的内容可能是错误/失败的，引申出C-RAG加入自我反思的步骤，对检索到的文档进行评估，进而采取不同的行动【检索-评估-行动】

      • 评估：正确/不正确/模糊，随之就是不同的行动：正确就进入知识提炼步骤、错误就知识重写，尝试联网搜索等、模糊就联网辅助生成答案。
      • 实现思路：可借助langgraph图结构来灵活构建条件判断和循环的复杂 RAG 流程

  • 格式化生成（与外部系统/工具交互）：

    • LangChain提供Output Parsers的工具处理LLM的输出，加入了如何格式化输出的指令（str json pydantic等）
    • Function Calling：相比于提示工程输出JSON，Function Calling实际上结构化输出更稳定，也有意图识别的功能，更是可以后续构建与外部世界的交互。

评估

  • 评估（评估RAG应用，量化追踪性能，幻觉定位问题根源）

    • 三元组：Query —— context（context_relevance） —— response（Faithfulness ）——Query（Answer Relevance）
      • Context_relevance：上下文是否和查询有关
      • Faithfulness：关注模型是否严格遵循上下文
      • Answer Relevance：关注模型是否真正完整有效回答了问题
    • 评估工作流：
      • 检索评估（上下文相关性，通过高质量的标注数据集白盒测试 Precision@k(前k个相关比例) Recall@k(前k个相关在所有文档比例) F1 MRR(靠前) MAP(通过平均精确率AP计算兼顾精确和排名)
      • 响应评估（忠实度和答案相关性，一般端到端测试，忠实度要保证答案能在上下文找到，答案相关性保证切题，没有冗余信息），方法有两种
        • 基于大语言模型的评估（质量高但成本高有偏见）：忠实度是将生成的答案分解为一系列独立的声明或断言，对于每一个断言，在提供的上下文中进行验证，答案相关性则是评估者需要同时分析用户查询和生成的答案。评分时会惩罚那些答非所问、信息不完整或包含过多无关细节的答案
        • 基于词汇重叠的经典指标（质量低但客观计算快成本低）：ROUGE 关注召回率，标准答案有多少个词语被生成答案所覆盖，来评估完整性，BLEU关注精确率，关注生成的词有效率，有长度过长的惩罚，衡量有效的词，METEOR 调和平均
