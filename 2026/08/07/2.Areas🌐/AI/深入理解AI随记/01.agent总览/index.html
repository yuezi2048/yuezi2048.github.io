01.agent总览

发表于2026-08-07|更新于2026-08-07|2.Areas🌐AI深入理解AI随记
|总字数:4.5k|阅读时长:13分钟|浏览量:

前言
实践在前，命名在后：

  • skill前，他们动态加载提示词+命令行执行解决提示词膨胀，系统状态栏来解决感知
  • harness前，他们就参考了cc方式解决不稳定、幻觉、越权、不遵循等问题
  • loop engineering前，他们就用到了proposer-reviewer的方式，来解决模型过早认为任务完成。

在名词还没流行前，如何提前知道怎么正确做：

  • Agent高要求业务 + 真实反馈：真实业务倒逼我们去构建harness等
  • Evalution机制：没有评估就没有进步

第一章 agent总览

agent = 大脑 + 眼睛 + 手脚

核心公式：Agent = LLM + 上下文 + 工具（脑子+眼睛+手脚）
(类比RL里的policy、observation space、Action Space)

公式：理解成模型和世界的接口：观察空间 in，动作空间 out【在模型固定情况下，就是考虑怎么重新定义/拓展这两个】
突破点（产品的演进大多数就是in/out的演进）：

  • Manus引入虚拟浏览器扩大观察空间，文件系统/代码执行/命令行扩大了动作空间（对早期各类agent的in/out取并集突破产品边界）
  • openclaw引入tele等消息渠道/本地gateway连接Notion等云应用/本地文件，丰富in，而早期Manus则要通过沙盒来上传文件等方式。

工具（topic 4 topic 2 API）：感知工具、执行工具、协作工具、事件触发工具、用户沟通工具
原则：从任务所需最窄能力起步，后续按需拓展。通用能力用于组合探索，专业工具约束高风险和强业务。

LLM：目前已经实现了模型即产品（通过后训练已具备工具调用等原生能力）
后续LLM的能力更新：

  • 当前上下文（topic 2）：成本低见效快，局限当前窗口
  • 外部知识（topic 3 - 5）：通过prompt/skill作为策略语言，确定性约束写成程序/harness，持久可审计，依赖context + func call
  • 模型参数（topic 7）：高维能力 泛化强，后训练训练回归成本高

context的组成（topic 2 API）：

  • 静态前缀【系统提示词（岗位设定 + topic 3记忆 + 动态环境） + 工具定义】
    • 2026年后 schema也支持动态按需加载末尾不破坏前缀
  • 动态消息历史 ：用户信息 【含RAG引入外部知识】 + 模型推理过程 【reasoning + tool_calls / reasoning + content】 + 工具结果

通过实验1-1的消融，对以上5个组件都各自去掉后出现了各自的问题，说明要实现agnet，上下文这五个组成部分缺一不可，同时也明确每一个组成的意义：

  • 静态前缀丢失，他直接没法调用工具
    • 工具定义是Agent行动的基石
  • 动态消息丢失，由于不知道上一步工具调用过程 / 推理过程 / 用户消息，直接循环/前后矛盾/失忆 每次都从头开始
    • 思考过程是多步推理的核心
    • 工具执行结果是闭环控制的核心
    • 历史消息保证任务连贯性，防止重复操作

协同模式：ReAct（reasoning + action + observe的循环）

  • 静态前缀定义
  • 结构化轨迹（user/assistant/tool，轨迹是每次LLM调用时看到的输入，每次工具执行结果会累加到轨迹中，给下一次调用）
    亮点是通过轨迹，在每一次调用都能保持对任务的全局感知，这也顺带有可解释性和可调试（进一步可以作为知识库，甚至作为语料训练Agent实现自我迭代）。

模型即产品的案例。

实验1-2 kimi K3的MOE混合专家模型，强化学习赋予了原生的自主决定何时调用搜索等工具的决策能力（注 工具本身还是需要定义，kimi是API内置了搜索/代码的工具），他的优势是长链工具调用的稳定（连续200次工具调用还能保证思考连贯）。

实验1-3 GPT5.6的原生内置搜索API完成”搜索-阅读-分析”的闭环迭代Deep Research，他提供了一个 Freeform Tool Calling，这意味着他的API调用相对传统JSON更灵活，他可以直接发送文本。还有一个意图澄清，他会询问问题来获取用户真实意图。弥合用户说什么和想要什么的差距

harness

这也是来源于面试官跟我提到的他们遇到一个头疼的难题：模型的幻觉问题（出现看似合理但不存在的工具/参数输出），以及选错工具 / 错误后无法恢复等问题。
本质是Demo和生产级产品的鸿沟，这是Harness要解决的问题。
Harness工程：围绕LLM（核心组件）构建的马鞍代码，参照公式理解为在上下文+工具基础上加三层保障：约束（约定能做和不能做）、验证（检错）、纠正（出错的兜底补救）

Agent = LLM + 【上下文 + 工具 + 约束 + 验证 + 纠正】= Model + Harness

最小工作只是Demo，扩展Harness三者新加的外壳才是可长期运行的生产项目。从能做事——> 能可靠地做事

举例，Claude Code 的精髓其实是围绕工具（文件读写，命令执行，搜索等）构建的保障机制：

  • 流程状态管理：追踪 Agent 当前执行到哪一步
  • 多层上下文压缩：当信息太多时自动精简
  • 权限分类：控制哪些操作需要用户确认
  • 熔断器（Circuit Breaker）：当错误连续发生时自动“断电”停止重试——就像家里电路短路时保险丝会自动跳闸，防止整个系统崩溃
  • 错误恢复机制：捕获异常、回滚到上一稳定状态、重试或交还给人类

**提示词工程 —— Context Engineering —— Harness、Loop Engineering —— Graph Engineering（2026.07）**的演变（层层包含，后者包含前者）

  • 背后的演进路线：优化自然语言指令 —— 系统管理LLM的in —— 在in的基础上考虑了模型所处的环境（约束+验证+纠错保证正常业务）、从单次运行扩展到跨轮次的持续自主运转（topic 10 多智能体，谁来发现next？什么时候验证？什么时候完成？） —— 更高级的编排视角（Agent循环、确定程序、人工组织组成一个执行图），节点定义能力，边定义路由/依赖，结构化状态沿边进行传递并在关键边界持久化。

当各家模型性能越来越接近，竞争的优势就是谁家Harness做得好。

工程实践：Langchain通过harness在Terminal Bench 2.0从30名外进入了前5。

在深入具体的编排模式和护栏设计之前，需要有一个可靠Agent构建的蓝图：

  • LLM的决策 依赖上下文 + 工具；
  • 可靠性保障：通过约束来预防错误，进一步通过验证发现问题，纠正来兜底。

从Anthropic的经验中，总结了构建有效Agent的方式：

  • 简单。从简单的方案开始，必要时才加复杂度，一开始的API调用直接依赖框架（每一层抽象意味着可能的额外调试成本）
  • 透明。显示规划步骤，执行决策，决策轨迹（为了调试，增加用户信任度，避免黑箱抽奖的情况）
  • 设计好的ACI（人机交互接口，一般指的是工具）：在Agent视角下设计接口。工具的参数命名要直观。在设计上要有防呆设计（让错误无法发生）

明确整体目标后，接下来展开课题：模型选型、编排模式、护栏与安全性。

模型选型

迭代很快，提供选择方向：准确率、价格、速度、模型策略/Reasoning/多模态 支持。

能力层面

  • 闭源模型：公认比较好的是OpenAI（GPT/o 系列）和 Anthropic（Claude 系列），闭源一般比开源强大但成本高。
  • 开源模型：成本低，可私有部署，微调定制，适合成本敏感/ 数据合规的业务。Deepseek / Kimi / GLM是国内比较好的模型

注：不要只看排行榜，要在你自己的任务上做评估，这就涉及到额外的问题：

  • 关注 策略边界（模型不一定支持接口的能力）：一些模型可能在【网络安全、模型蒸馏、模型提取、隐私数据、高风险操作】上有限制，所以在关键任务，需要有人工/其他合规模型兜底
  • 关注 Reasoning：一般多步任务都需要开，除非极少数Computer Use点击固定位置等少数单步简单任务
  • 关注 输出速度 / 多模态：在一些业务场景下，延迟 / 多模态支持是必须要考虑的

编排模式（工作流/自主）

编排：是上下文和工具的组织问题。决定上下文 在LLM调用中如何流动、工具如何调度、Agent执行路径是预先设定还是动态生成。

Anthropic等团队的经验证明：最好的实现是简单、可组合的模式。

能提示词+上下文解决的，就不要再引入Agent系统了；能固定子任务的场景，就可以直接用工作流；需要动态决策/灵活执行路径的场景才考虑Agent：

Agent实际上是用延迟和成本换取更好的任务性能，实际要权衡。

工作流是预先确定好了工作路径（节点内部可以LLM理解自然语言），优势：

  • 流程控制可控。不会出现LLM跳过/乱序等情况。
  • 安全性：提示注入/模型犯错只会影响当前节点。

局限相对也就是缺少了变通，出现了预设没出现的情况，可能需要预设的错误分支 / 人类兜底。

那么另外一条模式就是自主Agent，关键区别是自主Agent是依赖环境反馈实时决定，他可以自主规划，失败的时候可以调整。（当然也需要明确的停止条件【最终输出工具，无工具调用响应，错误，最大轮数等】，避免死循环），本质上就是LLM的ReAct循环。特别适合开放性的任务（如Coding Agent解决SWE-bench，Computer Use，迭代搜索和分析研究任务等），但也带来更高成本和复合错误风险。（需要在沙盒充分的测试，设置围栏和监控机制，关键节点要加入人机协作的check point）

实际可以考虑混合使用两者。严格合规流程用工作流，灵活决策的用自主Agent。像n8n就支持在可视化页面拖拽功能组件部署这两种Agent。

护栏与安全性

护栏是 Harness 中“约束、验证与纠正”层面的核心实现手段。（避免数据隐私泄露，声誉风险等），一般护栏是多个组合使用来提高韧性。

对齐（alignment，即让模型的行为与人类意图保持一致）

具体章节：【第二章（提示注入防护）、第四章（工具权限控制）和第五章（代码执行安全）】

护栏的引入会带来新问题：误杀掉正常的请求，如授权的模型蒸馏请求等，这提醒我们测试的时候除了错误的请求是否被拦截，还要测正确的请求能否正常完成

护栏分为三种：输入侧in、执行侧、输出侧out

  • in：相关性分类器（过滤偏离主题的）、安全分类器（越狱、提示注入等操纵模型）、内容审核（暴力歧视等内容）、基于规则保护（确定性的 黑名单、正则，可以防SQL注入等）
  • 执行：工具风险评级（操作是否可逆，权限，财务影响），高风险要人工审查。
  • out：PII过滤器（个人隐私信息），输出验证（回复要贴合品牌价值，正则等规则）

案例：Anthropic 的 Constitutional Classifiers

  • 规则驱动：用自然语言的宪法训练输入输出分类器
  • 上下文联合判断：提问和回答放一起检查（如对照提问才能发现食品调味料是暗指化学药剂）
  • 两级筛查：轻量探针检查所有会话，把可疑的交给强大分类器复审但不直接拒绝，在误报的情况下也不影响用户体验也减少成本。

人工干预（human-in-the-loop），人工可以更好的识别失败模式、发现边缘情况并建立健壮的评估周期。（客服等场景也能优雅地转人工，Coding可以将控制交给开发者），一般是两种情况触发：超过失败阈值、高风险操作。

注：安全是贯穿于每个环节都要关注的，是横切关注点。从表格中可以发现安全贯穿于模型、上下文、工具，再到多智能体的协作，甚至于社会层面。

Anthropic 在构建长时运行 Agent 时的实践展示了 Harness 设计如何解决模型本身无法解决的问题：

  • 他们将复杂任务分解为“初始化 Agent”（设置环境、分解任务列表）和“执行 Agent”（在每个会话中增量推进并留下清晰的交接产物），通过结构化的 Harness 解决了 Agent 在长任务中“上下文耗尽”和“过早声明完成”的问题。
  • 后续章节将逐一深入 Harness 的各个组件——第二章从最核心的上下文工程开始，第五章将专门展开 Harness 工程在 Coding Agent 中的完整实践。

思考题

★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文、还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

一般我会选择更强的模型，因为这代表的通用的推理能力，整体性能会更强。

但是这要结合业务，比如客服场景，公司内的规则对应上下文就比模型本身更重要，以及更多的工具，除非是Agent需要调用的工具很多，才会考虑有更多的工具。需要明确的是上下文越丰富并不是越好，Lost-in-the-middle，同时工具的增加，意味着AGI的维护需要更加严格控制，以及模型的增强意味着成本的增加。

★★★ ReAct 循环中，Agent 的每一次 LLM 调用都会看到完整的历史轨迹。随着轨迹增长，这种设计的成本是二次方增长的。有没有办法在不丢失关键信息的前提下打破这个二次方？

明白，本质上是因为循环中每次调用会复用前面的重复上下文，导致累加出现了二次方增长。

在我使用API调用的时候，他有一个概念叫作缓存输入，成本会比原先的正常输入少10倍，对于重复的上下文可以通过这个缓存拿就可以打破了。

★★ “模型即 Agent” 范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

我的理解是模型的自主性越来越高，那么意味着他的决策会考量的更多，在实际业务可能会不可控，因此Harness有必要限制模型贴合实际业务。

Agent的框架是进行适当的抽象，来帮助我们更专注设计业务。

★★ 消融实验中 “工具结果反馈” 的缺失导致 Agent 陷入无限循环。在生产环境中，除了工具结果缺失，还有哪些情况可能导致 Agent 无限循环？你会设计怎样的检测和终止机制？

还有一种情况，没有终止机制。有一些方法：设置最大循环次数、重试次数、正常工具调用检测。

★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？

codeX，感知了

★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？

★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是 “开放式” 的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

★★ 人工干预机制要求 Agent 能 “优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？

★★★ 引言指出 “好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。
