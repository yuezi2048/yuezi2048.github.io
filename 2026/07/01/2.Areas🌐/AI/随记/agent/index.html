智能体 = 在循环中自主调用工具的 LLM

Agent的范式

  • React（思考链COT + 纯行动结合——Thought-Action-Observation循环，推理让行动更有目的性，行动结果为下一步推理提供事实依据）
    • 优势：动态规划和纠错，可解释
    • 劣势：LLM的依赖（模型参数调优），多步执行效率、提示词的脆弱（few shots）、局部最优（分析输入输出）
    • 场景：引入外部知识，引入外部工具（与API交互、专业计算工具等）
  • Plan-and-solve（先规划再执行，需要维护状态管理维护每一步的执行结果，作为上下文给后续步骤，执行器则在当前上下文基础上专注解决当前任务）
    • 场景（数学题、整合多信息源、代码先整体再逐一实现）
  • Reflection（事后的自我校正循环，执行-反思-优化）
    • 优势：不单纯依赖工具反馈，有一个自纠错回路，构建了短期记忆（整条链路传递下来宝贵的经验），从一次性的任务执行到持续优化的过程（更可靠）
    • 成本：调用开销、任务延迟、提示词复杂度
    • 场景：关键业务代码、科研复杂逻辑推算、深度分析决策系统

低代码平台

  • 优势：技术门槛、开发效率、可观测性、提供标准化与最佳实践
  • Coze（友好的体验和丰富的插件生态，适合非技术/快速创意）
    • 优势：生态插件、可视化编排、灵活提示词、多平台部署发布
    • 缺点：没有MCP、插件配置复杂度、不能导入编排json
  • Dify（全栈开发能力，MCP接入等复杂场景，适合复杂业务编排，如多模态/复杂业务/企业级）
    • 全栈整合、便利性和专业性的平衡、企业级安全、工具集成、开源社区
    • 局限：学习成本、性能瓶颈、多模态支持不足、openAI 的API兼容
  • FastGPT（RAG体验，垂直领域回答，智能客服/私有知识库等场景）
    • 知识库、支持MCP、模型中立、可视化工作流
    • 缺点：模板生态弱、额度少、社区待完善
  • n8n（独特的连接编排能力，AI无缝接入工作流，业务集成/自动化）
    • 最大优势是开发效率，快速将逻辑转换成可视工作流，其次是集成度（gmail等），部署支持私有化部署
    • 局限：调试的繁琐、内置存储非持久性、虽然支持json但版本控制不如传统代码成熟、高并发的场景性能较纯代码弱

Agent框架

  • 框架的作用：代码复用、组件的解耦和拓展（模型层、工具层、记忆层可以比较容易切换策略，如记忆层滑动窗口/摘要记忆）、复杂状态管理（上下文窗口限制、历史信息持久化、多轮对话状态跟踪）、可观测性和调试（事件回调callbacks更优雅的在生命周期关键节点上报日志，明白整个运行轨迹）
  • AutoGen：
    • 优势
      • 流程化的可控/可预测：RoundRobinGroupChat的群聊模式非常清晰，并且有一个思想是Human-in-the-loop，专门有一个UserRole的角色（决策监督/最终验收）
      • 维护性：通过System Message可以高度定制一个专业角色完成任务，可复用/拓展，
      • 人类协作模式：无需复杂状态机/控制流，精力聚焦于定义角色（谁，做什么，如何做的流程控制），减少复杂任务门槛
    • 缺点
      • LLM不确定性：会导致对话偏离
      • 调试困难
  • AgentScope（消息驱动的架构，将流程优雅的映射成并发/异步的消息传递事件）
    • 结构化输出：避免传统状态机的僵硬，加大系统约束，增加可观测性/稳定性
    • 在该设计范式下，性能原生并发/容错优势
    • 缺点：复杂的成本（异步编程/分布式通信），简单的工程可能存在过度工程化风险
  • Camel（角色扮演涌现，轻架构重提示）
    • 相比硬编码的工作流更灵活高效，并且已经支持很多特性（与Langchain等生态联动、多模态、工具集成、多模型）
    • 缺点：
      • 提示词设计：调试复杂、一致性挑战（不同的LLM的一致性）
      • 协作规模：对话管理缺乏AutoGen的复杂路由、状态同步没有AgentScope的分布式状态管理、冲突没有一个仲裁机制
      • 任务实用性：在严格流程（LangGraph图结构）、复杂决策树（AutoGen的群聊多方决策）、大规模并发（AgentScope消息驱动分布式架构）都不是很好的选择
  • LangGraph
    • 流程可控性/可预测性：将流程定义为状态+节点+边的流程图，同时对循环原生支持，可以很方便构建反思的环节
    • 模块化：每个节点就是python函数，我们也可以很方便进行模块化，可以方便实现如human-in-the-loop的人机协作
    • 缺点：需要前期代码（定义流程图节点）、缺少涌现式交互（在开放性，不可预测的任务表现并不是擅长的），以及调试（主要是节点内部的错误/节点传递/边界条件跳转等多个环节排查）

Agent 记忆

  • 为什么要记忆（解决无状态的记忆遗忘-记忆系统维护、解决LLM内部知识的局限-RAG）
  • 记忆分类：
    • 工作记忆（短期记忆，高速访问，如当前会话前50条，在内存TTL）
    • 情景记忆（包含上下文信息基础，适合复盘回顾检索，事件序列-结构化/向量数据库）
    • 语义记忆（抽象知识规则，如用户偏好/长期遵守的指令，知识图谱-图向量数据库/向量检索）
    • 感知记忆（多模态信息，结构化/向量数据库）
  • RAG：
    • 朴素RAG（2020-2021 检索：TF-IDF或BM25来匹配字符，生成：直接拼接）
    • 高级RAG（2022-2023 检索优化：稠密嵌入的语义检索，生成优化：查询重写、文档分块、重排序等）
    • 模块化RAG（2023- 模块化自动化方向，检索加入了混合检索、多扩展查询、查询重写，生成优化：COT推理、自我反思和修正等）

上下文工程

  • 目标：什么样的上下文配置，最有可能让模型产出我们期望的行为
    • 对比提示词工程：上下文工程是在推理阶段，如何策划与维护“最优的信息集合（tokens）（提示+任何进入上下文窗口的信息,MCP,工具,系统指令,外部数据,消息历史等）
    • 上下文腐蚀：上下文token增加，回忆信息能力下降（所以上下文要看成有限资源，边际收益递减）
      • 虽然位置编码可以缓解上下文腐蚀，可以适配更长的序列，但牺牲token的准确理解，且上下文仍存在性能下降梯度
    • 维护思路：高信息密度的token，提高期望结果的概率
      • 系统提示词：清晰、直白（避免过于硬编码 / 过于空泛的两级）
      • 工具：要返回token友好的信息（职责单一、错误鲁棒、入参参数明确），要避免臃肿工具集（边界条件模糊），需要甄别出最小可用工具集（MVTS）
      • Few-shot：多样且典型
    • 上下文检索：embedding的一次性检索 ——> 及时上下文JIT（轻量引用，head/tail等方式动态加载）
      • 加载过程本身的元数据：目录层级/命名就是原生可利用的元数据MetaData
      • 渐进式披露：每一步的上下文会指导下一步的决策（工作记忆只保留当前必要子集，用记笔记的方式持久化的混合策略）
    • 长时程方案：压缩整合、结构化笔记、子代理框架
      • 压缩整合：上下文超过长度后，进行一次总结，并重载上下文窗口。
        • 优化思路：先优化召回（保证不遗漏），再优化精度（减少冗余内容）
        • 场景：适合长对话连续任务，上下文接力
      • 结构化笔记：固定频率写入上下文外的持久化存储，后续按需拉回
        • 极低成本维护持久状态，如TODO NOTES.md，关键依赖的索引，在经过多轮工具使用/重置后依然可以保证进度一致
        • 场景：适合里程碑/阶段性成果的编码场景，非编码场景的仿真/游戏的目标统计，也是需要的
      • 子代理架构
        • 主代理规划和总和，子代理在干净的上下文里调用工具干活，最后返回结果摘要
        • 在复杂任务上，关注点分离，适合并行搜索的科研/分析任务
    • GSSC上下文流水线说明：Gather-Select-Structure-Compress流水线，获取多源信息-选择-结构化-兜底压缩
      • 最佳实践：动态调整token预算、相关性计算生产环境优化、缓存、监控/日志、A/B测试（关键参数通过AB找到最优参数）

通信协议

通信协议（智能体与外部世界交互，智能体之间的协作）：

  • 为什么需要：传统的纯ReAct工具集成需要重复编写、能力扩展有限、以及协作能力缺失，通过设定标准化接口规范，通过统一方式访问外部服务（TCP/IP）
  • MCP：标准化智能体与外部工具/资源的通信方式，他的核心思想是上下文共享，他不是单纯的RPC协议（服务器不只提供内容，还可以提供如代码结构等上下文信息）
  • A2A：智能体之间的点对点通信，关注的是智能体之间的协作，类似于P2P，核心思想是对等通信，避免了中央协调器的单点故障、性能瓶颈，更灵活/拓展
  • ANP：目前概念性协议框架，目的是构建大规模智能体网络的基础设施。设计哲学是去中心化服务发现，通过服务注册、发现和路由机制动态发现网络服务，而不需要预先配置连接
    • 如果说 MCP 解决的是”如何访问工具”，A2A 解决的是”如何与其他智能体对话”，那么 ANP 解决的是”如何在大规模网络中发现和连接智能体”。
  • 实现一个MCP服务器的目标：封装业务流程、访问私有数据（内部数据库）、性能优化、功能定制拓展（集成专有算法模型/连接特定硬件设备）
    • Smithery 平台可以发布我们的MCP服务器供给其他用户使用

Agent-RL

  • 明确模型怎么来的：预训练（自监督，下一个词预测，得到强大的语言能力） + 后训练（对齐人类的偏好和价值观）

    • 监督微调SFT（遵循指令/对话格式）：给（prompt, completion）对，目标输出最大化正确输出概率
    • 奖励建模RM：评估回答质量，一个问题两个回答，目标是给更好的回答更高的分数
    • RL微调：建模奖励模型后，通过PPO等方式进行强化学习，训练目标是最大化奖励，但不要让偏离原始策略模型走太远（KL）
      • 传统RLHF（RL from feedback）依赖人工标注，RLAIF引申出AI来承担标注的任务（SFT生成候选回答，通过AI来评分排序，训练奖励模型，再用以强化学习，可以实现降本增效）

  • Agent RL：传统的后训练PBEFT（Preference-Based Reinforcement Fine-Tuning）关注的是单轮对话的质量优化，但在agnet的多步推理、工具使用、长期规划下就不适合，引申出适合Agent体质的Agent RL（思想是Agent拆解的每一步都认为是状态改变，每一步都有奖励，最终分数是每一步奖励的累计）

    • 马尔可夫决策过程： (S,A,P,R,γ)——状态空间、行动空间、状态转移函数、奖励函数、折扣银子
      • S：时间跨度>=1，并且包含历史观察和上下文
      • A：行动空间有工具调用、文本生成等
      • 转移函数：PBEFT没有状态转移，但AgentRL的状态会根据行动和环境的动态变化，调用搜索工具后，状态就会包含搜索结果
      • 奖励：Agent RL有多步奖励

  • 其他优化：

    • LoRA：模型微调时的参数变化可以用低秩矩阵表示。秩r典型参数值为 4-64

      原权重 W∈Rd×kW \in \mathbb{R}^{d\times k}W∈Rd×k 冻结不更新，微调增量 ΔW\Delta WΔW 不直接存储/训练，做低秩分解：ΔW=BA\Delta W = BAΔW=BA
      其中：

      • A∈Rr×kA \in \mathbb{R}^{r\times k}A∈Rr×k，随机初始化；
      • B∈Rd×rB \in \mathbb{R}^{d\times r}B∈Rd×r，初始化为全0；
      • 低秩约束：r≪min⁡(d,k)r \ll \min(d,k)r≪min(d,k)，秩远小于权重原始维度。

      前向计算融合两路特征：
      h=Wx+ΔWx=Wx+BAxh = Wx + \Delta W x = Wx + BAxh=Wx+ΔWx=Wx+BAx
      训练阶段只更新 A、B 两个低秩小矩阵，主干大权重 WWW 全程冻结。

      举直观例子：d=1024,k=1024,r=8d=1024,k=1024,r=8d=1024,k=1024,r=8

      • 全量参数：1024×1024=10485761024\times1024 = 10485761024×1024=1048576
      • LoRA 参数：8×(1024+1024)=163848\times(1024+1024) = 163848×(1024+1024)=16384
        参数量差距巨大。

    • GRPO(Group Relative Policy Optimization)：不需要 Value Model，使用组内相对奖励代替绝对奖励;简化训练流程，只需要 Policy Model 和 Reference Model，提高训练稳定性，减少奖励崩塌的风险。

Agent评估

智能体评估领域已经涌现出多个具有影响力的基准测试。下面介绍一些主流的评估基准和指标：

（1）工具调用能力评估

工具调用是智能体的核心能力之一。智能体需要理解用户意图，选择合适的工具，并正确构造函数调用。相关的评估基准包括：

  • BFCL (Berkeley Function Calling Leaderboard)[1]：UC Berkeley 推出，包含 1120+测试样本，涵盖 simple、multiple、parallel、irrelevance 四个类别，使用 AST 匹配算法评估，数据集规模适中，社区活跃。
  • ToolBench[2]：清华大学推出，包含 16000+真实 API 调用场景，覆盖真实世界的复杂工具使用场景。
  • API-Bank[3]：Microsoft Research 推出，包含 53 个常用 API 工具，专注于评估智能体对 API 文档的理解和调用能力。

（2）通用能力评估

评估智能体在真实世界任务中的综合表现，包括多步推理、知识运用、多模态理解等能力：

  • GAIA (General AI Assistants)[4]：Meta AI 和 Hugging Face 联合推出，包含 466 个真实世界问题，分为 Level 1/2/3 三个难度级别，评估多步推理、工具使用、文件处理、网页浏览等能力，使用准精确匹配（Quasi Exact Match）算法，任务真实且综合性强。
  • AgentBench[5]：清华大学推出，包含 8 个不同领域的任务，全面评估智能体的通用能力。
  • WebArena[6]：CMU 推出，评估智能体在真实网页环境中的任务完成能力和网页交互能力。

（3）多智能体协作评估

评估多个智能体协同工作的能力：

  • ChatEval[7]：评估多智能体对话系统的质量。
  • SOTOPIA[8]：评估智能体在社交场景中的互动能力。
  • 自定义协作场景：根据具体应用场景设计的评估任务。

（4）常用评估指标

不同基准使用不同的评估指标，常见的包括：

  • 准确性指标：Accuracy（准确率）、Exact Match（精确匹配）、F1 Score（F1 分数），用于衡量答案的正确性。
  • 效率指标：Response Time（响应时间）、Token Usage（Token 使用量），用于衡量执行效率。
  • 鲁棒性指标：Error Rate（错误率）、Failure Recovery（故障恢复），用于衡量容错能力。
  • 协作指标：Communication Efficiency（通信效率）、Task Completion（任务完成度），用于衡量协作效果。

参考设计

  1. BFCL：评估工具调用能力
    • 选择理由：数据集规模适中，评估指标清晰，社区活跃
    • 适用场景：评估智能体的函数调用准确性
  2. GAIA：评估通用 AI 助手能力
    • 选择理由：任务真实，难度分级，综合性强
    • 适用场景：评估智能体的综合问题解决能力
  3. 数据生成质量评估：评估 LLM 生成数据质量
    • 选择理由：通过这个案例可以完整体验如何使用 Agent 创造数据，评估数据的完整演示。
    • 适用场景：评估生成的训练数据、测试数据的质量
    • 评估方法：LLM Judge、Win Rate、人工验证
