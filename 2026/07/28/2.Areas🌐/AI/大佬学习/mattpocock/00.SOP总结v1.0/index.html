00.SOP凝结

发表于2026-07-28|更新于2026-07-28|2.Areas🌐AI大佬学习mattpocock
|总字数:2.5k|阅读时长:8分钟|浏览量:

参考地址

  • https://github.com/mattpocock/skills
  • https://github.com/mattpocock/slopwatch

一开始chatgpt下意识的给我总结了“软件工程化流程”，而经过纠错后我们发现 Matt Pocock 实际展示的是“AI Native 工作流”。

两者差异在于：

  • 软件工程流程倾向于：阶段化、文档化、提前规划

  • Matt 的 AI Native 方法倾向于：持续对齐、快速反馈、动态收敛

  • grill——目的是结晶化（crystallization），形成spec（destination），tickets（基于垂直切片的工单）

    • 错误模式：他明确反对“specs-to-code 然后修文档”的模式，认为“code is your battleground” 真正的对齐发生在 grilling 过程中，而不是事后修文档
    • prototype：他强调“Don’t waste time on specs: /prototype instead”，因为代码生产成本已经足够低，高保真原型比纸上 Spec 更有效
    • research：在grill过程中就顺带可以产出research产物（甚至派出了子agent去写markdown），并且/grill-with-docs会同时更新Context DDD ADR
    • to-spec：对于spec和DDD的区分，目前作者是收敛到了to-spec，实际上spec PRD在作者看来就是“destination document”（目的地），而不是详细设计说明书
    • wayfinder：对于不止一次grill的工作，他用到了wayfinder作为决策地图，在工作流中对应将决策拆成可并行的 Decision Tickets

  • TDD优先于编码约定：to-tickets 之后的 implement 几乎总是驱动 /tdd。笔记中应当强调“先写失败测试再实现”是防止 AI 作弊的核心机制。

  • Code review不能在长对话里做，否则会带“sediment”（沉淀的错误假设）

  • 迭代的复杂度维护：他在直播中提到了利用improve-codebase-architecture进行架构维护，减少项目更改的难度（即项目复杂度），防止熵增

在第二轮对话中，我们对文档主要修正了三个认知偏差：

  1. 从“流程”升级为“反馈循环”（理解了反馈循环，就知道为什么必须垂直切片

所以之前的版本虽然方向没错，但确实有两个偏差：

  1. 把流程画成瀑布式

  2. 把文档的重要性放高于实际反馈

而 Matt 更强调：

文档不是目的，共识和反馈才是目的。

除去工作流本身，补充一些作者的一些有价值的观点：？为什么要纯净上下文review？答案都是“为了让反馈环更快、更干净、更难被 AI 作弊”）

  • 对齐循环：Grill ↔ Research / Prototype
  • 规划循环：Spec ↔ Tickets（blocking 关系形成 DAG）
  • 执行循环：Ticket → TDD → Implement → Fresh-context Review →（必要时回流）
  • 架构循环：定期 Improve-codebase-architecture
  1. 从“文档驱动开发”升级为“DDD + Context Engineering + Spec-driven Development”（我们理解为AGI层面的共识驱动开发）
  • 人和 AI 使用同一套精确术语（ubiquitous language）
  • 决策的“为什么”被记录下来（ADR）
  • 变更的边界和验收标准被写清楚（Spec + Tickets）
  1. 补上 Prototype、TDD、Fresh Context 三个 AI Native 关键环
环节 核心作用 如果不做会发生什么
Prototype 用可丢弃的高保真产物回答“逻辑对不对 / UI 好不好” 在抽象空间里打转，Spec 写得很漂亮但落地后发现方向偏了
TDD（Red-Green-Refactor） 强制 Agent 先写失败测试，再实现 Agent 容易“先实现再补测试”，测试变成实现的镜像，失去保护作用
Fresh Context 实现与 Review 必须分会话 长对话留下 sediment（错误假设、过时上下文），Review 质量大幅下降

在第三轮对话中，Gemini pro导师补充的内容，我认为不是简单增加几个点，而是在修正整个方法论的“底层操作系统”。

之前版本偏向：

“AI Native 工程流程是什么？”

现在应该升级为：

“为什么这个流程能在 AI 时代有效？它如何控制 AI 带来的不确定性？”

最终版应该补充控制不确定性的章节，而不是简单堆概念。

最终被重塑为一份标准的工程化 Manifesto（宣言）或团队级 SOP。它的逻辑非常严密，非常适合在技术面试中作为你的核心方法论进行展示，或者直接引入到你日常的复杂项目（例如需要高度解耦 UI 与核心逻辑的系统）开发中。

AI Native 项目开发方法论：控制不确定性与优化反馈流

参考来源： 基于 Matt Pocock (Skills & Slopwatch) 等前沿实践经验总结。

核心理念： 传统的软件工程往往倾向于“阶段化、文档化、提前规划”，而在 AI 时代，开发范式必须转向“持续对齐、快速反馈、动态收敛”。在这一体系下，文档不是目的，共识和真实反馈才是真正的目的。

一、 核心范式变更：从“瀑布流水线”到“高频反馈环”

不要将 AI Native Workflow 理解为从 Idea 到 Review 的单向流水线。AI Native 开发真正优化的不是“如何让 AI 写更多代码”，而是“如何让错误尽可能早地暴露”。

它是一个动态嵌套的反馈循环，任何时候发现问题（需求不清、UI 未定、架构混乱）都可以随时回流：

  • 对齐循环 (Grill ↔ Prototype / Research)：消除需求歧义与设计错误。

  • 规划循环 (Spec ↔ Tickets)：形成带有阻塞关系 (DAG) 的工单，防止目标漂移。

  • 执行循环 (Ticket → TDD → Implement → Fresh Context Review)：保障代码落地质量。

  • 架构循环 (Improve-codebase-architecture)：定期治理，防止系统熵增。

二、 驾驭 AI 不确定性的四大工程支柱

AI 的生成速度极快，必然会产生临时代码、粗糙实现或不优雅的结构——这被称为 Slop（可控混乱）。我们的目标不是绝对消灭 Slop，而是通过工程手段控制其传播范围。

1. 垂直切片 (Vertical Slice)：限制爆炸范围

  • 定义：一个工单 (Ticket) 必须是端到端的交付，而不是按技术层拆分。

  • 反面模式：让 AI 依次去“完成数据库 -> 完成 API -> 完成前端”。这种方式在各层集成前，无法获得真实的用户反馈。

  • 正确模式：让 AI 实现一条贯穿的业务线（如“用户上传 PDF -> 解析 -> 索引 -> 搜索返回答案”）。这样不仅能立即获得功能体验反馈，就算 AI 产生了脏代码，影响范围也被死死限制在这一条执行路径上。

2. 隔离与纯净 (Fresh Context)：抵御认知污染

  • 痛点：在同一个长对话中完成设计、编码和审查，AI 会记住过时的错误假设和实现细节，产生 Context Sediment（上下文沉淀），导致 Review 质量断崖式下降。

  • 规则：严格执行“单 Ticket 单会话原则”。

  • 实施：执行 Agent 加载 Spec 和 Ticket 完成编码后，必须开启一个全新的 Review Agent 会话，仅加载核心 Context 和最终代码进行审查，用未知视角去挑战实现。

3. 接缝 (Seam) 与 深度模块 (Deep Module)：建立防腐层

  • Seam 的第一价值不是重构，而是可测试性。通过提取纯净的业务逻辑函数或 API Hook 作为“接缝”，我们将复杂的 UI 渲染与底层逻辑彻底剥离。只要暴露出的接口稳定，内部逻辑随 AI 怎么优化都不会破坏系统。

  • 警惕过度抽象：AI 极易制造诸如 AbstractFactoryProvider 等过度设计的浅模块。架构设计应坚守“少量深模块”原则，避免无意义的嵌套增加心智负担。

4. 强制 TDD：防止 AI 作弊

  • 机制：在执行工单时，要求 Agent 必须先写失败测试，再写实现代码（Red-Green-Refactor）。

  • 目的：如果不强制 TDD，Agent 极易“先写实现，再根据实现补测试”，导致测试沦为实现的镜像，彻底失去业务保护作用。

三、 AI Native 落地工具链与步骤

在实际执行中，人与 AI 应当形成多角色团队（子 Agent 模式）来推进项目：

  1. 结晶化 (Grill)：拒绝“Specs-to-code 然后修文档”的模式。真正的对齐发生在对抗性追问中，用以梳理未决定的需求。若存在复杂的分支决策，使用 Wayfinder 生成决策地图。

  2. 高保真验证 (Prototype)：代码极其廉价，不要在抽象空间打转，直接通过生成原型代码来验证逻辑或 UI 方向是否跑偏。

  3. 共识沉淀 (To-Spec)：形成涵盖精准统一语言 (DDD) 和架构决策记录 (ADR) 的目的地文档 (Destination Document)。

  4. 切片派发 (To-Tickets)：将目标拆解为可独立验证、带依赖关系的执行工单。

  5. 业务验收 (Evaluation)：特别针对 RAG 等复杂应用，代码能跑不等于效果正确，必须在验收环节加入准确率、延迟等多维度的业务评估环。

四、 重新定义工程师的核心价值

在 AI 时代，软件开发者的核心角色不再是“写代码的人”，而是向更高维度的系统掌控者演进：

  • 决策者：决定做什么、不做什么、优先级排序以及技术取舍。

  • 上下文工程师：建立领域语言 (DDD)，保存架构决策 (ADR)，并为 AI 划定极其明确的安全边界。

  • 质量守门人：负责最终结果的验收，敏锐发现 AI 潜藏的错误假设。

💡 核心总结 (Elevator Pitch)

“AI Native 开发绝不是简单地让 Agent 替代工程师写代码，而是通过严密的上下文工程和极速反馈机制，确保 Agent 在可控的边界内可靠执行。 其工程核心不是试图‘提前设计完美架构’，而是在 Grill、Prototype、Spec、垂直切片、TDD 和纯净上下文审查之间构建高频循环。通过严格限制代码 Slop 的传播范围并持续进行架构治理，我们能够在保持系统高度可维护性的同时，充分享受 AI 带来的十倍速迭代红利。”
